# Processware 전문가용 표준 프로세스 관리·현장 지원 웹 애플리케이션 기획서

버전 0.6 · 작성일 2026-10-06 · 개정일 2026-10-07 · 기획 기준: 초기 전문 운영자 1명 / 개인 서버·원격 접속 / 전문가 관리·현장 파일/연동 사용

## 1. 제품 정의

Processware는 조직에서 적용할 표준·가이드·매뉴얼을 분석하고, 근거가 연결된 표준 프로세스 자산을 구축하며, 실제 산출물을 증적에 연결하고, 점검 결과를 개정으로 환류하는 전문 업무 도구다. 사용자는 AI Agent와 대화하며 목표와 판단을 전달하고, Agent는 자료 조사·계획·전문 Agent 위임·실행·검토·개정을 이어 간다. 원문·요건·자산·증적은 같은 작업 공간의 결과 패널에서 확인한다.

**제품 목적은 전문가가 관리하는 표준 프로세스를 프로젝트 현장에 배포하고, 현장 산출물을 정비하여 감사·감리·인증·심사 증적과 회사 지적 자산으로 환류하는 것이다.** 모든 구성원이 표준 구축·Harness 과정을 알아야 할 필요는 없다. 전문가의 구축/관리 경로와 현장의 절차·템플릿 사용 경로를 구분한다.

전문가의 주 사용 방식은 **대화로 목표 정의 → Agent 계획·실행 → 근거와 변경 검토 → 중요한 결정 승인 → 작업 지속**이다. 사용자는 관리 필드를 일일이 채우기보다 Agent에게 업무 목표·수정·판단을 전달한다.

**핵심 구축 기능은 ① 다중 표준 통합 구축과 ② 기존 기준선에 추가 표준 적용이다.** 공통 업무는 통합하고 고유 의무는 추가 단계·조건·양식 또는 별도 활동으로 반영하며, 원천 표준별 요건·판·충족 상태를 보존한다. 단일 표준 구축도 지원한다.

**프로세스 자산을 개선하는 동시에 그 자산을 만드는 Harness도 검증하며 개선한다.** 자산 편집·피드백을 원인 분석과 개선 후보로 연결하고, 격리 시험·승인·버전 활성화로 이후 작업의 품질을 개선한다. 한 번의 편집이 공통 규칙을 자동 변경하지 않는다.

제품의 핵심 가치는 문서 생성량이 아니라 **원천 요건 → 적용 판단 → 프로세스 자산 → 수행·백필 증적 → 점검 결과 → 개선·개정**의 연결을 보존하는 데 있다. 첫 버전은 사용자 본인이 조직별 프로세스 자산을 관리하는 개인 서버형 웹 앱이다.

### 기존 정의와 웹 정책의 조정 사항

1. README와 일부 가이드의 디렉터리·큐 경로 표기가 다르다. 시작 시 실제 트리를 검사하고 경로 레지스트리를 만들며, 문서의 경로를 고정값으로 복사하지 않는다.
2. plan 명령에는 main 메타 등록·push와 산출물 branch 정책이 있다. 웹 앱은 서버 내부 버전 저장을 기본으로 하고 원격 push는 별도 설정으로 분리한다. 기존 지침에서 해당 작업을 억제할 수 있는지 검증 전에는 읽기 전용 모드로 시작한다.
3. backfill의 상단 원칙은 MAT 읽기 전용이라고 쓰지만 마지막 단계는 MAT-005 갱신을 요구한다. 웹 권한은 REC 신규 작성·MAT-005 인덱스 갱신만 허용하고 POL/PRO/WI/TMP/EX는 보호한다.
4. 백필 수동 WI 지정에 confidence 100%를 부여하는 기존 규칙은 웹에서 '수동 지정'으로 표시한다. 유사도 점수와 사용자의 선택을 혼동하지 않는다.
5. 원문이 없을 때 LLM 내부 지식으로 표준을 추정하는 경로는 참고 초안에만 허용한다. 근거 확인 전 공식 적용요건·승인 자산·점검 결론으로 승격하지 않는다.
6. 1인 사용은 자체 점검으로 운영한다. 사용자 역할을 바꿔도 같은 사람의 독립성은 확보되지 않는다. 독립 심사와 다인 PCB quorum은 후속 범위다.

## 4. 목표와 성공 지표

| 목표 | 측정 방법 | 첫 버전 완료 기준 |
|---|---|---|
| 근거를 잃지 않는 자산 구축 | 승인 자산의 적용요건 링크와 출처 확인 | 대상 요건에 대한 출처 누락 0건; 제외는 사유 기록 |
| 실제 문서의 증적 활용 | 백필 REC의 원본·필드별 출처·WI 버전 연결 | 승인 백필의 원본 해시·출처 링크 100% |
| 유지관리의 안전성 | 초안/승인본 비교·재개·충돌 검사 | 미승인 작업의 승인본 덮어쓰기 0건 |
| 개선 환류 | finding → 개선안 → 개정본 → 재점검 연결 | 대표 사례 1건의 폐쇄 루프 완료 |
| 업무 시간 절감 | 같은 10개 자료를 수동 처리한 기준 시간과 비교 | 출시 후 실측; 초기 목표 30% 단축은 검증 가설 |

문서 수·유사도 점수·AI 응답만으로 준수 또는 인증 적합을 보장하지 않는다. 표준 커버리지와 실제 이행 점검을 별도 지표로 보여 준다.

## 5. 업무 시나리오

### UC-01 표준 프로세스 신규 구축

조직 프로필 등록 → 허용된 원천 자료 업로드 → 구조·요건 추출 → 원문 대조 및 적용/제외 판단 → 업무 흐름 선택·수정 → POL/PRO/WI/TMP/EX 초안 생성 → 규칙 QA·출처 검토 → 사용자 승인 → 버전 기준선 확정.

### UC-02 기존 조직 매뉴얼 정비

기존 매뉴얼을 As-Is 기준 자료로 분류 → 외부 표준 요건과 대조 → 중복·상충·누락 확인 → 기존 자산과 새 자산 대응 관계 검토 → 필요한 부분만 개정 → 개정 사유와 영향 기록.

### UC-03 실제 산출물 백필

과거 보고서·회의록·평가표 업로드 → 추출 및 OCR 필요성 확인 → WI 후보·범위·파일 그룹 검토 → 필드별 원문 매핑 → 미확인 필드와 상충 표시 → 사용자 확정 → `legacy_evidence` REC 생성. 원본의 작성일·작성자·승인 사실은 자료에서 확인된 내용만 기록한다.

### UC-04 개정 표준 반영

새 판 등록 → 조항·요건 변경 비교 → 영향을 받는 자산·TMP·수행 기록 목록 확인 → 개정 범위 승인 → 변경 초안 생성 → 기존 승인본과 비교 → 새 기준선 활성화. 과거 기록은 수행 당시 기준선을 유지한다.

### UC-05 점검 결과로 개선

승인 기준선과 증적을 선택 → 자체 이행 점검 또는 외부 표준 GAP 분석 → 근거와 미평가 확인 → finding 확정 → 개선 큐 → 원인 분석·개정 계획 → 자산 개정 → 효과 확인 후 종결.

### UC-06 WI에 따라 새 기록 작성

승인 WI와 TMP 선택 → 단계별 입력·검토 → 필요한 사용자 승인 → 신규 REC 생성. 백필 REC와 구분하여 해당 시점의 수행 흔적을 저장한다.

### UC-07 다중 표준 통합 구축 — S1 핵심

사용자: **A와 B를 통합해서 우리 조직의 프로세스를 만들어 줘. 공통 업무는 한 번만 수행하도록 해 줘.**

Agent는 조직·표준 판·적용 범위·자료 권한을 확인하고 `integrate_new` 계획을 만든다. 표준별 원자 요건을 추출한 뒤 동등/부분 중첩/포함/고유/상충/불확실 관계를 근거와 함께 제안한다. 공통 활동은 하나로 구성하고 고유 의무는 조건·단계·필드 또는 별도 활동으로 반영한다. 원 의무를 삭제하거나 공통 요약으로 대체하지 않는다. 사용자는 불확실한 관계·적용 판단·상충을 검토하고 표준별 커버리지와 자산 변경 묶음을 확인하여 발행한다.

### UC-08 기존 기준선에 추가 표준 적용 — S1 핵심

사용자: **현재 A 기반 프로세스에 B를 추가해 줘. 기존 문서와 번호는 최대한 유지하고 필요한 변경만 제안해 줘.**

Agent는 기존 승인 기준선과 적용 표준 구성 판을 고정하고 `augment_baseline` 계획을 만든다. B의 요건을 기존 자산과 비교해 재사용 가능/보완 필요/신규 필요/상충/판단 대기로 분류한다. 무변경 자산은 같은 ID·revision·hash를 유지하며 링크만 추가하는 변경도 검토 대상에 포함한다. 영향 있는 자산에만 새 판을 만들고, A의 기존 의무가 손실되지 않는지 회귀 검사한다. 사용자 승인 후 새 구성과 변경 묶음을 하나의 기준선으로 발행한다.

### 두 핵심 모드의 통합 원칙

| 관계 | 설계 반영 | 보존할 정보 |
|---|---|---|
| 동등 | 공통 활동·자산으로 재사용 | 양쪽 원 의무·판·출처·충족 근거 |
| 부분 중첩 | 공통 활동 + 표준별 추가 조건 | 공통 부분과 남은 독립 의무 |
| 포함 | 포함 방향·조건 검증 후 활동 재사용 | 주체·대상·추가 의무·적용 scope |
| 고유 | 별도 활동 또는 기존 단계·필드 확장 | 해당 표준의 고유 근거·수행 조건 |
| 상충 | 범위 분리 또는 근거 있는 판단 | 해결 사유·권한·조건·미해결 상태 |
| 불확실 | 별도 유지·검토 요청 | 후보 관계·근거 부족·판단 대기 |

기준 표준은 구조·용어의 출발점이다. 다른 표준의 의무를 자동으로 낮추거나 최대 엄격도만으로 상충을 해소하지 않는다. 적용 의무의 미해결 누락·상충은 공식 발행을 차단한다. 분석 단계의 GAP·초안·보류는 가능하다.

표준별 커버리지는 각각의 적용 원 요건으로 계산한다. 공통 업무 수를 줄여도 표준별 분모를 합치지 않는다. 구성 변경·추가·제거·판 교체는 새 구성 판과 기준선으로 관리하며 기존 REC·평가는 당시 구성과 판을 보존한다. 추가/제거의 기본 영향·회귀 검사는 S1, 실제 증적·열린 평가·run까지의 전체 영향 분석은 S2다.


### UC-09 자산 정밀 편집에서 Harness 개선으로 — 핵심

사용자가 WI를 수정하면서 **담당자와 승인자가 계속 빠져. 앞으로 이 조직의 업무지침에서 확인하도록 Harness도 보완해 줘**라고 요청한다. 현재 문서의 수정과 별도로 전후 diff·수정 사유·생성 run·실제 Harness 판을 연결한 개선 후보를 만든다. Agent는 원인 가설과 조직 scope를 제안하고 지침·템플릿·지원되는 역할 검사 설정의 변경안을 격리 작성한다.

사용자는 후보와 기존 Harness를 동일한 허용 평가 사례에서 실행한 결과를 비교한다. 역할 누락 개선, 고유 의무 보존, 조직별 예외, 백필 미확인·승인·권한 회귀를 확인한다. 실패·평가 미완료 후보는 활성화할 수 없다. 변경안·시험 허용·실제 활성화는 구분한 결정으로 기록한다.

승인된 새 release는 이후 작업에 적용한다. 진행 작업은 기존 버전으로 재개하고 과거 승인 자산을 자동 변경하지 않는다. 사후 결함·수정·비용은 사실과 비교 조건을 함께 관찰하며 문제가 있으면 호환성 검증 후 이전 Harness를 신규 작업용으로 복귀한다. 관련 자산 개정은 별도 개선·발행 흐름이다.


### UC-10 전문가 관리·프로젝트 배포·현장 회수·증적·지적 자산

전문가는 회사 기준선에서 프로젝트 자산을 선택·테일러링하고 승인한 절차·DOCX/XLSX 빈 템플릿·작성/제출 안내를 파일 또는 검증된 시스템 adapter로 배포한다. 현장 구성원은 익숙한 도구로 작성·제출하며 표준 구축/Harness UI를 방문할 필요가 없다.

사용자: **프로젝트 P에 이 기준선의 절차와 템플릿을 배포하고, 돌아온 산출물을 정비해서 심사 제출용 증적 묶음으로 만들어 줘. 범용 사례는 회사 지적 자산 후보로도 정리해 줘.**

Agent는 원본·배포/WI/TMP 판을 추적하고 임의 작성·필드 누락·상충을 provenance가 있는 정비 초안으로 만든다. 전문가가 실제 사실을 확인·검토하여 REC를 발행하고 목적별 증적 패키지를 내보낸다. 사후 정비가 원래 승인·수행 사실을 생성하지 않는다. 사례·교훈의 재사용 권한·범위·정보 제거를 검토한 뒤 지적 자산으로 승인하고 표준/Harness 개선은 별도 흐름으로 연결한다.

## 7. 대화 중심 Agent Workspace

전문가의 기본 진입 화면은 **업무 대화 + 작업 계획 + 근거·결과 패널**이다. 왼쪽에는 조직과 진행/완료 업무, 중앙에는 사용자와 Agent의 대화·계획·진행·결정 카드, 오른쪽에는 선택한 원문·요건·자산·증적·diff를 둔다. 원천자료·자산·백필 메뉴는 대화 중 필요한 상세 패널로 접근하고 독립 관리 화면은 보조로 제공한다.

Agent는 요청의 목적을 구체화하고 자료를 조사해 계획을 세운 뒤 전문 agent와 도구로 실행한다. 사용자는 필요한 자료·업무 지식·중요 판단을 제공한다. Agent가 입력을 채우거나 추천해도 그 사실과 원문에서 확인된 수행 사실은 구분한다.

| 업무 | 사용자의 대화 | Agent의 실제 작업 | 확인·결정 |
|---|---|---|---|
| 구축 | 이 자료들로 우리 조직의 개발 표준 프로세스를 만들어 줘 | 조직·범위·자료 권한 확인, 요건 추출·흐름·자산 초안 계획 및 실행 | 적용 판단·상충·범위 확인, 변경 묶음 발행 승인 |
| 통합 | A와 B를 통합해 공통 업무는 한 번만 수행하게 해 줘 | 원 의무 대응·공통/고유 설계·표준별 커버리지·QA | 관계·상충·고유 의무 검토와 통합 기준선 발행 |
| 추가 | A 기준선에 B를 추가하고 필요한 부분만 바꿔 줘 | 기존 snapshot 고정·재사용/보완/신규 분류·최소 diff·A 회귀 검사 | 추가 범위·기존 의무 보존·새 기준선 발행 |
| 정비 | 이 절차는 과도해. 소규모 프로젝트에 맞게 줄여 줘 | 선택 자산 판과 근거 요건 조회, 제외 가능 범위 분석, 새 초안·diff | 생략한 의무와 테일러링 사유 확인 |
| 백필 | 이 산출물을 백필해 줘. 앞의 세 파일은 같은 회의야 | 후보 WI·그룹·필드·출처를 실제 객체에 반영, 미확인·상충만 질문 | 매핑·필드 snapshot 명시 확정 |
| 개선 | 이 GAP을 해소하고 영향 있는 절차도 개정해 줘 | 원인 가설·영향 분석·개정 계획·초안·QA·재점검 연결 | 개정 범위·발행·실제 효과 확인 |
| 프로젝트 배포 | 이 프로젝트에 사용할 절차와 템플릿을 배포해 줘 | 프로젝트 기준선·테일러링·파일/adapter·manifest·권한 projection | 배포 판·대상·범위 승인 |
| 증적·지적 자산 | 돌아온 문서를 정비해 심사 자료와 재사용 사례로 만들어 줘 | 원본/판·필드 provenance·사실 확인·증적 패키지·범용 후보 | 정비·증적 공개·재사용 권한/범위 검토 |
| Harness 개선 | 앞으로 이 조직의 WI에서 역할 누락을 검사해 줘 | 편집 피드백·원인·scope·후보 diff·기준/후보 격리 비교·release | 평가 결과·적용 scope·새 버전 활성화·복귀 |
| 재개 | 지난번 작업 어디까지 했지? 계속 진행해 줘 | 저장된 목표·결정·현재 run 상태 조회, 안전한 단계에서 재개 | 바뀐 기준선이나 남은 질문만 확인 |

### 대화는 실제 업무를 제어한다

자연어 요청은 조직·대상 revision에 묶인 작업 명세 또는 typed 변경 명령으로 변환한다. 서버가 권한·스키마·현재 판을 검사하고 실제 저장·실행한 결과를 대화 카드로 보고한다. 채팅 기록만 남기거나 저장하지 않은 변경을 완료라고 설명하지 않는다. 사용자에게는 목표·근거·결과를 보여 주며 내부 실행 명세를 직접 작성하게 하지 않는다.

### Agent가 진행할 일과 사용자가 판단할 일

Agent는 허용된 자료 조회·추출·분석·범위 안 초안 작성·규칙 검사·제한적 수정·작업 재개를 진행한다. 사용자는 업무 목표·적용 판단·상충 해결·의미 있는 변경 승인과 실제 수행/효과의 확인을 맡는다. 자료 제공 외에 사람이 모든 문서·메타·매핑을 먼저 입력해야 하는 흐름을 기본으로 삼지 않는다.

승인은 대화에서 가능하다. 대상·변경 내용·판·영향·승인 범위를 카드로 제시한 뒤 해당 카드의 승인 또는 명확한 응답을 durable Decision으로 저장한다. 계획에 대한 동의와 최종 기준선 발행 승인은 구분한다. 좋아·계속해가 무엇에 대한 응답인지 불명확하면 확인한다. 매 단계 질문하기보다 중요한 결정에서 확인한다.

### 대화 기억과 작업 상태

대화 메시지·구조화 업무 기억·실제 run 상태를 함께 저장한다. 기억에는 목표·제약·선택 조직/판·사용자 결정·미해결 질문·허용 범위를 포함한다. 긴 대화의 요약은 원 메시지와 결정 기록을 참조하며, 요약이나 모델 기억이 실제 저장 상태를 덮어쓰지 않는다. 재접속 후에도 승인한 선택을 다시 입력받지 않고 중단 지점에서 이어 간다.

업무 패널은 근거 검토와 정밀 편집 수단이다. 백필 표·원문 비교·자산 편집을 사용할 수 있으나 같은 업무의 일반 수정은 대화로도 완료할 수 있어야 한다. 패널에서 수정한 내용 역시 같은 객체·대화 맥락·변경 이력에 반영한다.

### 구체적인 기본 UI

첫 화면은 **어떤 프로세스 업무를 진행할까요?**라는 목표 입력창·자료 첨부·시작 예시·이어할 업무다. 기본 탐색은 새 업무/진행 업무/검토 대기/완료/자료·자산 찾기이며 문서 유형별 관리 메뉴는 보조 패널로 재배치한다.

1440px에서는 업무 목록 240px, 대화 520px, 산출물 Canvas 608px를 기본으로 한다. 폭이 좁아지면 대화/결과 탭으로 전환하며 입력·선택 대상·작업 상태를 유지한다. composer에는 조직·기준선·적용 표준 판·통합/추가 모드·문서 판·선택 문단 chip과 자료 첨부가 있다. 한글 IME를 보호하고 접수 실패 시 작성문을 보존한다.

Agent의 출력은 Plan/Question/Progress/Evidence/Artifact/Change/Mapping/Decision/Outcome 카드로 표시한다. 카드의 근거·결과·승인은 실제 객체·revision·run·gate·receipt와 연결된다. 초안/발행/효과 확인, 화면 연결 끊김/실제 취소를 구분한다. 모델이 만든 임의 HTML을 실행하는 방식 대신 검증된 컴포넌트를 사용한다.

Canvas는 본문·변경 비교·근거·이력을 제공한다. 문단 선택 후 **선택한 부분을 대화로 수정**하면 해당 판/범위 chip이 composer에 들어간다. 사용자는 **이 문단만 간단히 해 줘**로 수정하고 diff·근거를 검토한다. **이 수정 되돌리기**는 새 변경 이력, **다른 대안도**는 승인본을 바꾸지 않는 A/B 초안이다.

백필은 Agent가 WI·그룹·필드를 채운 뒤 예외 중심 카드로 검토한다. **앞의 세 파일은 같은 회의야 / 승인자는 미확인으로 둬**가 실제 매핑/필드 수정으로 이어진다. 전체 표는 필요할 때 비교용으로 확장한다. 최종 카드 **백필 매핑·필드 확정**과 **기준선 발행**은 별도 결정이다.

최신 공식 문서에서 확인한 패턴은 대화와 산출물 공간, 도구 결과에 따른 UI, 접을 수 있는 계획/진행, inline 승인, 수정/복구다. Processware 적용은 이를 조직 자산·증적·개정의 버전 관리에 연결하는 제품 설계 판단이다. [AI SDK Generative UI](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces), [AI Elements](https://github.com/vercel/ai-elements), [Microsoft Agent design, 2026 갱신](https://learn.microsoft.com/en-us/agents/design-guidelines/human-centered-design).

화면별 위치·카드 payload·문구·구축/백필/개정 대화·상태 전이·폭별 동작은 별도 `05_Processware_대화형_UI_UX_상세명세.md`와 요구사항정의서 §15를 제품 규범으로 적용한다.

## 9. 아키텍처 제안

브라우저 Agent Workspace → TLS reverse proxy → Conversation Orchestrator/FastAPI API → 업무 계획·typed domain tools → PostgreSQL 운영 DB → 전용 worker → HarnessAdapter → 격리 작업 디렉터리 → 승인 후 Vault/Git 기준선 반영.

개인 서버의 기본 서비스는 reverse proxy, API/UI, worker, PostgreSQL이다. 파일과 Vault는 persistent volume, 내부 버전은 private Git으로 관리한다. 사용자 운영 DB는 PostgreSQL, 기존 Redmine 매핑 SQLite는 연동 컴포넌트 내부 저장소로 구분한다. 초기에는 Redis·벡터 DB·LangGraph를 필수로 추가하지 않는다.

Vault는 승인 자산 내용의 기준이며 DB는 검색 색인과 업무 상태·승인·작업 기록의 기준이다. 두 저장소에 같은 본문을 각각 자유 수정하지 않는다. 승인 전 작업은 격리 공간에 저장하고, 승인 대상 hash와 base version을 확인한 뒤 한 개의 변경 묶음으로 발행한다. 발행 중 장애는 commit ID와 manifest로 복구한다.

### 실행 엔진 전략

`HarnessAdapter`는 실행 시작·이벤트 수신·승인 재개·취소·상태 조회·산출물 목록 기능을 제공한다. UI가 슬래시 명령 문자열을 조합하거나 임의 셸 실행을 제공하지 않는다. 7개 업무 종류를 명시적 작업 명세로 전달한다.

대화 orchestrator는 의도·맥락·계획·설명·중간 지시를 담당하고, 기존 전문 agents는 각 단계의 업무를 담당한다. 승인·자료 권한·발행 상태는 모델이 아니라 서버가 결정한다. S0에서 자연어 목표 하나가 실제 계획·run·대화 승인·재개로 이어지는지와 현재 하네스의 실제 승인·재개 기능이 안전하게 어댑터화되는지 검증한다. 성공하면 기존 엔진을 연결하여 S1을 구축한다. 실패하면 command/agent 지침을 유지하면서 제어가 필요한 실행·HITL 부분을 SDK로 구현한다. 장기적으로 독립 엔진이나 여러 AI 제공자로 교체해도 업무 데이터·화면은 유지한다.

### Harness 개선 구조

자산 기준선과 Harness release는 독립적으로 버전 관리한다. FeedbackCase가 자산 diff·원 의무·생성 run·EffectiveHarnessSnapshot을 연결한다. 후보 평가 runner는 운영 쓰기와 분리하고, 릴리스 검토 후 새 작업용 활성 포인터만 전환한다. 공통 Harness→조직 overlay→표준/자산 유형 조건을 해결하되 보호된 권한·승인 규칙은 덮어쓸 수 없다. 새 실행 코드는 S2의 격리 변경·검증된 배포 아티팩트로 적용한다.


## 10. 운영·권리·품질 정책

자료는 조직 범위와 이용 권한을 등록한다. 원문 보관, AI 전송·처리, 인용·산출물 내보내기 권한을 각각 구분한다. 권한이 불명확한 파일은 저장·수동 검토는 가능하되 AI 처리와 외부 제공을 차단한다. ISO 공식 정책은 AI 프롬프트를 통한 활용까지 제한하므로, 표준 구매 사실만으로 AI 이용 허용을 추정하지 않는다. 이용할 자료의 구체적 허용 범위를 확인한 후 처리한다. [ISO 공식 저작권·AI 이용 정책](https://www.iso.org/copyright.html)

원본은 불변으로 보관하고 변경본은 새 revision으로 저장한다. 실제 승인자·작성일·수행 사실이 미확인인 부분은 AI가 채워 넣지 않는다. AI 점수는 추천 점수로 표시하며 승인 또는 준수 확률로 설명하지 않는다. 자체 점검과 독립 심사 결과는 구분한다.

원격 서버에서 API·파일·다운로드에 모두 인증을 적용한다. 브라우저 코드에 AI 키를 넣지 않는다. 승인되지 않은 변경은 공식 자산에 반영하지 않으며, 작업 취소·예산 초과·오류에서도 원본과 승인본을 보존한다.

## 14. 개정 기록

0.2: 사람의 입력·관리 화면을 주 진입점으로 두었던 0.1을 대화 중심 Agent Workspace로 개정했다. 대화 계획·실제 업무 변경·맥락·기억·중간 지시·명시 승인과 패널의 역할을 제품 핵심으로 정의했다. 기존 데이터·추적성·버전·권한 규칙은 대화 실행에도 적용한다.

0.3: 대화 UI의 홈·탐색·composer/context·카드·Canvas·selection·결정·복구·되돌리기·폭별 동작을 구체화했다. 최신 공식 사례 근거와 Processware 설계 판단을 구분하고 상세 UI·UX 명세를 추가했다.


0.4: 다중 표준 통합 구축·기존 기준선에 추가 표준 적용을 S1 핵심 기능으로 확정했다. UC-07/08, 대응 관계·공통/고유 의무·증분 변경·회귀·표준별 커버리지·구성 판 관리와 대화 검토 동선을 구체화했다.


0.5: 자산과 Harness의 이중 개선을 제품 핵심으로 추가했다. UC-09, HAR-01~10, 후보·평가·scope·불변 릴리스·작업별 버전·관측·복귀, S2 코드 검증 경로와 UI-14를 반영했다.


0.6: 전문가/전문팀 관리와 현장 사용을 분리하고 프로젝트 선택·배포·회수·비정형 정비·증적·회사 지적 자산화를 목적·UC-10·S2 핵심 기능으로 추가했다. 초기 전문 운영자 1명의 개인 서버 배포 조건은 유지하고 모든 직원에게 구축 계정을 요구하지 않는다.
