# Processware AI Agent 기반 프로젝트 작업 공간 신규 기획서

버전 1.0 · 2026-10-07 · 신규 기획 기준선 PW · 상태: 검토용 기획안

> 승인된 표준 프로세스 템플릿으로 프로젝트 작업 공간을 생성하고, 사람과 AI Agent가 구조화된 산출물 Vault에서 업무를 수행·검증·승인하는 환경.

## 1. 기획의 위치와 목적

### 1.1 별도 신규 기획의 범위

본 문서는 기존 표준 프로세스 자산 구축 기획의 후속 확장인 **내부 현장용 프로젝트 작업 공간**을 독립적으로 정의한다. 하나의 Processware 플랫폼 안에서 기능과 권한 영역을 구분하며, 별도 제품이나 별도 설치를 전제하지 않는다.

기존 문서 기준선 0.6, 기능·화면 구조 기준선 0.4 및 기존 요구사항 번호·개발 단계는 수정하지 않는다. 본 문서의 PW 요구사항과 P1~P3 단계는 신규 범위에만 적용하며, 기존 S1~S3 단계와 자동으로 대응하지 않는다. 구현 완료를 의미하지 않는다.

| 영역 | 책임 | 주 사용자 |
|---|---|---|
| 기존 표준 구축 영역 | 원천 표준 분석·통합, 조직 프로세스 자산 구축, 구축 Harness 평가·개선 | 전문가·전문팀 |
| 신규 프로젝트 작업 공간 | 승인 템플릿 적용, 프로젝트별 조정, 업무 Agent 실행, 산출물·증적·실행 기록 관리 | 프로젝트 담당자·검토자·승인자 |
| 연결 계약 | 템플릿 릴리스 수신, 적용 버전 추적, 개선 제안 전달 | 배포 책임자·프로젝트 책임자 |

**목적:** 반복 입력과 문서 서식 편집을 줄이고, 사람은 목표 설정·전문 판단·검토·승인에 집중하게 한다. 프로젝트가 실제 수행한 내용과 근거를 축적하여 감사·감리·인증·심사 자료 및 검토된 조직 지적 자산으로 재사용한다.

### 1.2 제품 원칙

- 구조화된 콘텐츠를 기준 정보로 관리한다. Office·PDF는 기존 자료 입력과 필요한 배포·보고·제출을 위한 형식이다.
- 대화는 업무 수행 인터페이스이며, 중요한 결정·변경·승인은 자산과 실행 기록에 반영한다.
- Agent의 제안·초안·적용 완료를 구분한다. 권한과 확정된 실행 규칙은 검증 로직에서도 집행한다.
- 현장 사용자는 표준 통합이나 Harness 개발 과정을 학습할 필요가 없다.
- 프로젝트의 변경은 조직 표준을 자동 수정하지 않는다. 검토된 제안을 별도 환류한다.
- 파일 정비나 AI 작성으로 수행 사실·날짜·서명·승인을 만들어내지 않는다.

## 2. 사용자와 대표 업무

### 2.1 역할과 권한

| 역할 | 수행 업무 | 기본 통제 |
|---|---|---|
| 전문팀·템플릿 관리자 | 승인 템플릿 제공, 조직 규칙·업무 Agent 릴리스 관리 | 프로젝트 내용 접근은 별도 권한 필요 |
| 프로젝트 책임자 | 공간 생성, 테일러링 승인, 구성원·실행 도구 관리 | 조직의 필수 통제는 임의 완화 불가 |
| 업무 담당자 | 대화로 산출물 작성·수정, 업무 수행, 제출 | 승인된 항목은 새 수정안으로 변경 |
| 검토자·승인자 | 근거·변경·누락 확인, 반려·승인 | 역할 분리 요구를 실제 사용자 기준으로 검사 |
| 감사·조회 사용자 | 허용된 기준선·증적 열람 | 프로젝트별·자산별 범위 제한 |
| 업무 Agent | 위임된 자료 조회, 작성 제안, 검증, 허용 도구 실행 | 사용자 위임과 Agent 정책의 교집합 권한 |

초기에는 개인 서버의 운영자 1명이 프로젝트 업무까지 시범 수행한다. 역할을 전환해도 독립 검토로 표시하지 않는다. 다른 현장 사용자의 접속은 P2의 인증·격리·역할 검증 후 개방한다.

### 2.2 대표 시나리오

**A. 프로젝트 생성:** “승인된 소프트웨어 개발 프로세스로 고객 A 프로젝트를 만들어줘.” Agent가 필요한 범위·역할·템플릿 버전을 확인한다. 생성안과 제한사항을 검토하면 빈 산출물 구조, 규칙, 업무 Agent 구성이 준비된다.

**B. 산출물 작성:** “이 고객 자료에서 요구사항 초안을 만들고 모호한 부분을 정리해줘.” 원본을 보존하고 요구사항 후보·근거·미확인 사항을 제시한다. 사용자가 수정·확정한 항목을 Vault에 등록한다.

**C. 변경 영향 분석:** “이 요구사항을 바꾸면 설계와 시험에 어떤 영향이 있지?” 연결된 항목의 특정 버전으로 영향 분석을 제시한다. 승인 범위 내에서 수정안·후속 업무를 생성하고 기존 검토의 유효성을 재평가한다.

**D. 제출·승인:** 필수 항목이나 증적이 없으면 제출을 차단한다. 검토자가 보완 요청을 하면 사유와 대상 위치를 연결한다. 승인 시 검토한 버전과 결과를 고정한다.

**E. 종료·환류:** 프로젝트 기준선과 증적 색인을 생성한다. 재사용 후보는 민감 정보·이용 권한을 검토하고 조직 자산 개선 제안으로 전달한다. 제안 수신은 조직 표준 변경 승인이 아니다.

## 3. 프로젝트 생성과 템플릿 적용

### 3.1 템플릿 계약

상위 구축 영역에서 전달하는 템플릿 릴리스는 다음을 포함한다. 기존 파일 묶음에 없는 정보는 새 계약으로 보완하며, 기존 자산만으로 실행 가능한 Agent가 자동 완성되었다고 간주하지 않는다.

| 구성 | 내용 |
|---|---|
| 정적 정의 | 목적·범위·활동·역할·필드·산출물 유형·관계 |
| 동적 정의 | 상태·전이·선행 조건·이벤트·후속 작업·예외 처리 |
| 규칙 | 필수사항, 정합성·권한 제약, 적용 제외·지원 제한 |
| 근거 | 표준 의무, 조직 결정, 승인된 운영 규칙의 출처 |
| 실행 구성 | 업무 Agent 지침, 도구 계약, 승인 지점, 허용 동작 |
| 검증 자료 | 정상·위반·경계 평가 사례, 지원 대상·한계 |
| 릴리스 정보 | 고유 식별자·버전·해시·승인·호환성·필요 권한 |

모든 자산 요소는 동적 규칙 검토 상태를 갖는다: **정의 완료·적용 없음·추가 판단 필요**. 적용 없음에는 이유를 남긴다. AI가 도출한 규칙 후보는 승인된 표준 의무와 구분한다. 필수 통제의 추가 판단이 남으면 운영 배포를 차단하고, 탐색용 초안 공간은 미검증 상태로 허용한다.

### 3.2 생성·테일러링 절차

1. 승인된 템플릿 릴리스를 선택하고 프로젝트 목적·범위·기간을 입력한다.
2. 적용 활동·산출물·역할을 선택하고 조정 이유를 기록한다.
3. Agent 도구·데이터 접근 범위·승인 방식·실행 대상을 설정한다.
4. 누락·규칙 충돌·권한·대상 지원 능력을 검사하고 생성안을 검토한다.
5. 템플릿 릴리스, 프로젝트 조정판, 실행 설정을 고정하고 공간을 활성화한다.

생성은 승인된 정의를 참조하고 프로젝트별 데이터를 초기화하는 작업이다. 이전 프로젝트의 실제 기록·승인·증적·계정·인증 정보는 복제하지 않는다. 작성 예시는 실제 기록과 구분한다. 공통 정의는 불변 릴리스로 참조하고 프로젝트 변경은 별도 조정판으로 관리할 수 있다.

### 3.3 변경과 갱신

프로젝트는 적용한 템플릿·규칙·Harness 버전을 고정한다. 조직 템플릿 개정 시 현재 항목·상태·필드 값·검토·실행 중 작업에 대한 영향과 이전 계획을 제시한다. 승인 후 점검된 범위에 새 버전을 적용한다. 이전 이력은 보존한다.

실행 중 작업은 시작 시 고정한 정의 버전을 따른다. 마이그레이션 시 해당 작업을 완료·중단·재계획할지 결정해야 한다. 구성 복원과 외부 업무 변경의 되돌리기는 구분하며, 외부 변경이 모두 복구될 수 있다고 가정하지 않는다.

## 4. 산출물 Vault와 콘텐츠 관리

### 4.1 정보 구조

Vault는 프로젝트의 요구사항·설계·시험·결정·업무·증적을 식별자로 연결하는 논리적 저장·관리 계층이다. 특정 폴더나 Git만으로 Vault 기능을 대신하지 않는다. 개인 서버의 초기 구현은 구조화된 메타데이터·관계·상태를 데이터베이스에, 원본·첨부를 파일 또는 객체 저장소에 보관하는 구성을 제안한다. Git 연계는 선택 구현이다.

| 객체 | 관리 내용 |
|---|---|
| ProjectWorkspace | 범위·구성원·적용 릴리스·조정판·실행 설정 |
| AssetItem / AssetRevision | 산출물 항목 식별자, 구조화된 필드·서술 블록, 버전·상태 |
| TraceLink | 요구사항·활동·산출물·증적 사이의 관계 유형과 버전 |
| SourceRecord | 원본 위치·해시·수집 시점·출처·권한 |
| Decision / Approval | 판단·사유·대상 버전·승인 주체·시점·유효성 |
| ExecutionRun / EventRecord | 수행 단계·이벤트·규칙 판정·도구 결과·복구 기록 |
| Baseline / EvidencePackage | 선택한 항목 버전·관계·증적·누락의 불변 묶음 |

검색 색인과 AI 임베딩은 기준 데이터에서 재생성 가능한 보조 자료로 둔다. 자산 접근 권한은 검색·추천·Agent 도구 결과에도 적용한다.

### 4.2 작성·편집·검토

항목별 직접 편집과 선택 영역 AI 수정을 함께 제공한다. Agent 변경안에는 대상 식별자·기준 버전·변경 차이·근거·연관 영향이 포함된다. 기준 버전이 바뀌면 기존 변경안을 그대로 적용하지 않고 충돌을 검토한다.

서술 편집기는 콘텐츠 블록을 편집하며 상태·관계·승인·실행 규칙은 별도 구조로 관리한다. 페이지 여백·목차·번호 등 출력 서식은 출력 템플릿이 담당한다. 기존 파일 수입은 원본을 보존하고 매핑·변환·미확인 값을 검토한 후 등록한다.

예시 산출물 상태는 **초안 → 검토 요청 → 검토 중 → 승인 → 대체/보관**이다. 실제 상태와 전이는 템플릿별로 정의한다. 승인 후 본문 변경은 새 수정판으로 생성하며 기존 승인판을 덮어쓰지 않는다. 승인은 특정 버전과 연결하고, 관련 항목 변경 시 재검토 필요 여부를 규칙으로 판단한다.

## 5. Agent 중심 인터페이스와 업무 실행

### 5.1 기본 화면

프로젝트를 명시적으로 선택한 뒤 대화와 작업 패널을 함께 연다. 현재 프로젝트·적용 버전·선택 자산·Agent 실행 상태를 항상 확인할 수 있어야 한다.

| 화면 | 주요 기능 | 다음 흐름 |
|---|---|---|
| PW-UI01 프로젝트 홈 | 프로젝트·담당 업무·보완 요청·최근 활동 | 생성 또는 작업 공간 진입 |
| PW-UI02 생성·조정 | 템플릿·범위·역할·규칙·도구 설정과 검증 | 승인 후 작업 공간 |
| PW-UI03 대화 작업실 | 목표 대화, 실행 계획, 질문, 진행·중단, 결과 패널 | 산출물 편집·변경 검토 |
| PW-UI04 Vault 탐색·편집 | 구조·검색·관계·필드·서술·원본·버전 | 수정안·제출 |
| PW-UI05 변경·검토·승인 | 변경 차이·근거·영향·보완·승인 | 반영 또는 반려 |
| PW-UI06 실행·정합성 | 규칙 위반·판정 불가·이벤트·실패·복구 | 보완·재실행 |
| PW-UI07 기준선·증적·출력 | 범위 선택·누락 검토·스냅샷·내보내기 | 제출·종료 |
| PW-UI08 설정·연동·개선 | 구성원·권한·버전 갱신·ALM 매핑·환류 | 설정 검토·적용 |

### 5.2 실행 흐름

**의도 전달 → 권한이 있는 맥락 조회 → 계획·수정안 제시 → 규칙 검증 → 필요한 사람의 승인 → 변경 적용·도구 실행 → 결과 확인·실행 기록 → 후속 업무**.

사전 승인된 저위험 초안 작업은 정책 범위에서 자동화할 수 있다. 기준선 발행, 보호 필드 변경, 대외 배포, 승인 및 권한 변경 등은 정의된 사람의 승인 지점을 둔다. UI의 승인 버튼과 채팅 문구는 서버가 발급한 승인 요청에 연결하고 승인자의 권한과 대상 버전을 다시 검사한다.

실행은 준비·대기·진행·사람 응답 대기·성공·실패·중단·부분 완료 등으로 구분한다. 진행 표시에는 실제 단계와 도구 결과를 사용한다. 중단은 향후 동작을 멈추는 것이며 이미 수행된 외부 변경의 자동 취소를 뜻하지 않는다. 승인 요청과 작업은 대화 밖에서도 조회·재개 가능해야 한다.

### 5.3 Harness의 두 역할

상위의 **자산 구축 Harness**와 현장의 **업무 실행 Harness**를 별도 버전·평가 대상으로 관리한다. 현장 Harness는 선택한 프로세스 자산, 프로젝트 맥락, 도구·권한·검증·복구 설정으로 구성한다. 모델 가중치 학습을 전제하지 않는다.

현장 실행에서 발견한 오류는 근거와 재현 조건을 포함해 개선 후보로 전달한다. 검토된 평가 사례로 후보 Harness를 시험하고, 승인된 릴리스를 프로젝트가 선택적으로 적용한다. 프로젝트 수정 내용이 공유 Harness에 자동 반영되지 않는다.

## 6. 동적 프로세스와 실행 정합성

### 6.1 규칙 정의

| 규칙 유형 | 예시 | 집행 시점 |
|---|---|---|
| 필드 | 고위험 항목은 대응 책임자·계획 필수 | 저장 또는 제출 |
| 관계 | 시험 결과는 요구사항과 시험 대상 버전에 연결 | 제출·기준선 발행 |
| 상태 | 검토 완료 및 승인 권한이 있어야 승인 가능 | 상태 전이 전 |
| 실행 순서 | 선행 분석 완료 후 설계 검토 시작 | 업무 시작 |
| 이벤트 | 요구사항 변경 시 연결된 시험의 재검토 요청 | 변경 확정 후 |
| 예외 | 승인된 예외의 기간이 끝나면 보완 요청 | 기한 도래 |

규칙에는 식별자·적용 범위·조건·근거 유형·심각도·위반 조치·예외 가능 여부·버전을 기록한다. 규칙 충돌, 미존재 참조, 도달 불가 상태, 순환 의존성, 필수 승인 누락을 검사하고 실행 사례로 보완 검증한다.

판정은 **통과·위반·판정 불가·적용 제외**로 나눈다. 데이터나 외부 결과가 없으면 판정 불가로 처리한다. ‘필드 작성 완료’와 ‘증적 내용이 충분함’, ‘내부 검사 통과’와 ‘외부 심사 적합’을 구분한다. 의미 판단이 필요한 사항에는 전문가 검토를 연결한다.

### 6.2 이벤트와 트랜잭션

이벤트는 식별자·출처·프로젝트·대상 버전·발생/수신 시각·인과 관계·적용 정의 버전을 갖는다. 내부 변경과 이벤트 발행의 일관성을 보장하고, 외부 수신은 중복 제거·버전 검사·재시도 기록으로 처리한다.

동일 이벤트의 중복 수신으로 업무를 중복 생성하지 않는다. 지연·순서 역전·동시 변경에는 현재 판과 선행 조건을 검사한다. 처리 실패는 재시도 가능 여부, 단계별 완료, 보완 작업 및 수동 조치 경로를 남긴다. 여러 시스템에 걸친 변경은 단일 원자적 성공을 가정하지 않는다.

외부 연동은 규칙별로 **대상 직접 집행·별도 서비스 집행·사후 탐지·지원 불가**를 표시한다. 사후 탐지를 사전 차단으로 표시하지 않는다. 필수 차단이 필요한 규칙을 구현할 수 없으면 운영 적용을 막거나 허용된 대체 통제를 승인받는다.

## 7. ALM 연동·출력·증적·지적 자산

### 7.1 세 가지 실행 모드

| 모드 | 실행 위치 | 기획 범위 |
|---|---|---|
| 내부 실행 | Processware 작업 공간·Vault·Agent | 신규 기획의 우선 검증 대상 |
| 외부 ALM 실행 | 대상 ALM의 업무·상태·필드, Processware의 Agent 지원 | 제품별 어댑터로 단계적 확장 |
| 혼합 실행 | 내부 콘텐츠와 외부 업무를 연계 | 객체·필드·상태별 기준 시스템 지정 필요 |

Redmine·Jira·Codebeamer는 연동 후보이다. 제품·버전·배포 방식·권한에 따른 자동 구성 범위는 구현 전 실제 API와 환경에서 확인한다. 본 문서는 세 제품의 모든 필드·워크플로를 자동 구성할 수 있다고 보장하지 않는다.

동기화 계약은 외부 식별자·버전·필드 매핑·기준 시스템·삭제 정책·중복 방지·충돌 처리를 포함한다. 내부 내용이 외부에 반영되고 돌아올 때 반복 갱신이 발생하지 않도록 출처와 동기화 판을 기록한다. 구성안 검토, 실제 반영, 외부 확인을 구분한다.

### 7.2 출력·증적·환류

승인된 콘텐츠와 선택 버전에 출력 템플릿을 적용한다. 웹 열람과 Markdown/JSON 묶음을 우선 제공하고, 보고·제출 사례에 따라 PDF·DOCX·증적 색인 등을 추가한다. 원본·보정 이유·사후 확인·미확인·적용 규칙·증적 링크를 연결한다.

증적 패키지는 목적·범위·기간·기준선·선택 기준·해시·누락·제외·한계를 포함한다. 출력 생성은 외부 제출이나 인증 합격을 뜻하지 않는다. 허가되지 않은 원문 표준·민감 정보·다른 프로젝트 자료는 공개 대상에서 제외한다.

조직 재사용은 프로젝트 종료 후 자동 수행하지 않는다. 후보 추출 → 이용 권한·민감 정보 점검 → 일반화·검토 → 조직 자산 또는 Harness 평가 사례로 승인하는 절차를 둔다.

## 9. 구현 단계와 검증 계획

### 9.1 P1 — 개인 프로젝트에서 한 사이클 검증

개인 서버의 사용자 1명이 한 템플릿과 한 실제 프로젝트로 생성 → 대화 작성 → 정밀 편집 → 검증 → 자체 검토 → 기준선 → 출력까지 수행한다. 순차 흐름과 핵심 변경 이벤트를 우선 구현한다. 승인 분리 기능의 데이터 구조는 두되 한 사람의 활동을 독립 승인으로 표시하지 않는다.

필수 기반은 인증·원격 접속 보호, 프로젝트 경계, 버전 검사, 서버 규칙 검사, 작업 큐·실행 기록, 비밀정보 분리, 백업과 복원이다. 재료는 승인된 템플릿 하나, 실제 요구사항·설계·시험 자료, 사람이 확인한 정답·누락 사례다. 원본 수입은 시범 자료에 필요한 파일 유형부터 검증하며 모든 Office 변형을 지원한다고 선언하지 않는다.

### 9.2 P2 — 현장 사용과 통제 확대

다중 사용자와 역할 분리, 동시 수정, 예외·병렬 검토, 템플릿 갱신, 증적 패키지·보고 출력, 조직 환류를 추가한다. 다른 현장 사용자를 초대하기 전 권한 누출·승인 우회·동시성 검증을 통과해야 한다.

### 9.3 P3 — ALM 실행 확장

실제 대상 하나를 선정하고 버전·권한·API 지원 범위를 확인한다. 기존 Redmine 코드 재사용 가능성을 평가하되 자동으로 지원 완료로 간주하지 않는다. 구성안 → 승인 → 배포 확인 → 수행 기록 회수 → 충돌·복구까지 검증한 후 Jira·Codebeamer 등으로 확장한다.

| PW-AT12 | 프로젝트 개선 환류 | 조직 자산·공유 Harness의 무승인 변경 없음 |

### 9.5 성과 측정

시범 프로젝트에서 기존 방식과 작업 범위·품질 기준을 맞추고 비교한다. 입력·편집·검토·재작업을 합한 총 시간, 전문가 수정량, 실제 누락 발견, 근거 추적 성공, 재사용 비율을 측정한다. 응답 속도·모델 비용·실패율도 함께 기록한다. 목표 수치는 최초 시범 기준선을 얻은 후 확정하며 현재 문서에서 생산성 향상을 보장하지 않는다.

## 10. 비기능 조건·위험·후속 결정

| 항목 | 기획 조건 |
|---|---|
| 접근과 데이터 보호 | 개인 서버 원격 인증·전송 보호, 프로젝트 권한, Agent 최소 권한, 첨부·출력 동일 통제 |
| 변경 일관성 | 버전 검사·원자적 내부 변경·이벤트 발행 일관성, 외부 부분 실패 추적 |
| 신뢰와 복구 | 승인판·기준선 불변, 백업·복원 검증, 삭제·복원·보존 정책 |
| AI 신뢰성 | 출처·미확인 구분, 문서 내부 지시를 명령으로 실행하지 않음, 평가와 승인 경계 |
| 사용성 | 한국어 입력·선택 편집·실행 재개·명확한 상태, 대화와 작업 화면 연결 |
| 비용·운영 | 실행별 모델·도구 비용과 상한, 오류·감사 기록, 인덱스 재구축 가능성 |

주요 위험은 과도한 범위 확대, AI 결과 검토 부담, 규칙 도출 오류, 자료 접근 누출, 동기화 충돌이다. P1의 실제 업무 사이클로 효과를 확인하고 P2·P3 확대 여부를 결정한다. 범용 ALM의 모든 기능 대체, 모든 파일 형식 완벽 수입, 자동 인증 판정, 모델 자동 학습, 복잡한 분산 업무의 전면 자동화는 초기 범위에 포함하지 않는다.

후속 결정은 시범 프로세스·프로젝트 선정, 구조화 콘텐츠 필드 계약, 첫 승인·예외 사례, 모델·실행 환경·데이터 처리 정책, 보존·백업·복구 목표, 첫 ALM 대상·버전, 출력 서식 선정이다. 편집기와 UI 구성요소의 최종 선택은 정밀 편집·충돌·변경 비교·출력 시제품으로 검증한다.
