# Processware 요구사항정의서

버전 0.6 · 2026-10-07 · 대상: 초기 전문 운영자 1명의 개인 서버 관리 앱 + 현장의 프로젝트 배포물 사용

## 1. 목적과 문서 적용

원천 기준에서 조직 표준 자산을 구축하고 실제 증적을 연결하여 지속적으로 개정하는 업무를 구현 가능한 요구사항으로 정의한다. 기획서의 제품 범위를 세부 기능·업무 규칙·데이터·상태·화면·인수 기준으로 구체화한다.

사용자가 확정한 조건은 초기 전문 운영자 1명, 현장 구성원의 배포 절차/템플릿 사용·산출물 제출, 개인 서버 설치·원격 접속, 표준 프로세스 생성·관리·백필·개선이다. 0.6은 전문가의 표준 관리와 현장의 적용 결과 사용을 분리하고 프로젝트 배포·회수·정비·증적/지적 자산화를 S2 핵심으로 한다. 이전 0.5의 자산 편집·대화 피드백을 Harness의 검증된 개선으로 연결한다. S1은 지침·템플릿·지원 설정의 후보/격리 평가/승인/버전·복귀 루프를, S2는 실행 코드의 격리 변경·검증·배포를 포함한다. 이전 0.4의 다중 표준 통합 구축·기존 기준선에 추가 표준 적용을 S1 핵심 기능으로 명시한다. 두 모드는 원천별 의무·판·출처를 보존하고 표준별 커버리지·상충·증분 변경·회귀 검사를 제공한다. 기존 0.3의 구체적인 대화 UI·상황별 카드·Canvas·연결 복구·되돌리기를 포함하여 AI Agent와 대화하며 업무를 빌드하는 방식을 기본 진입점으로 정의한다. 사용자는 목표·수정·중요 판단을 전달하고 Agent가 구조화 업무 객체와 실행을 관리한다. 최초 적용 표준·파일 형식 우선순위·AI 엔진은 미확정이며 기본 제안을 사용한다. 아래 성능·용량·보존 숫자는 **제안 목표**이며 실제 서버와 대표 자료로 조정한다.

요구사항은 정의 상태다. 저장소의 Markdown 지침·설계안·PoC 설명은 신규 웹 제품의 구현 완료 증거가 아니다. 정규식·번호·스키마 등 결정적 검사는 Python 규칙 코드로 재사용하고, AI 판단·HITL·실행 복구는 실제 엔진 연동으로 검증한다.

문서 기준선: 저장소 main 트리 `e9534276d69a22a76d8fe01f3a45faa8b20d8072`. 조직 및 자산의 과거 revision은 별도 불변 기준선이다. 웹 앱 개발 중 바뀐 요구사항은 ID를 유지하고 변경 사유·판을 추가한다.

## 2. 용어와 유형

| 용어 | 정의 |
|---|---|
| 원천 기준 | 표준·법규·가이드·기존 조직 매뉴얼처럼 영속 적용요건의 근거가 되는 자료 |
| 실제 증적 | 보고서·평가표·회의록 등 과거 또는 현재 업무 수행을 설명하는 자료 |
| 적용요건 | 원천의 요건 중 조직에 적용하는 항목과 적용/제외 판단 |
| POL / PRO / WI | 정책 / 절차 / 업무지침. 서로 다른 추상도와 수행 상세를 갖는 문서 |
| TMP / EX / REC | 빈 양식 / 작성 예시 / 실제 수행 또는 백필 기록. 예시를 증적로 취급하지 않음 |
| MAT / REF | 추적성·관리표 / 참고자료 |
| 기준선 Baseline | 특정 시점에 승인된 요건·자산 revision 집합과 manifest |
| ChangeSet | 하나의 검토·승인·발행 대상으로 묶인 파일·링크·버전 변경 |
| Run / Gate | 하네스 작업 실행 / 해당 실행의 사용자 검토·승인 대기 지점 |
| Backfill | 원본 수행 자료를 WI/TMP에 매핑하여 출처와 한계를 보존한 REC로 정리 |
| legacy_evidence | 백필 증적 유형. 현재 표준 절차를 당시 실제 이행했다는 자동 증명은 아님 |
| HarnessRelease / EffectiveHarnessSnapshot | 불변 실행 구성 버전 / 공통 release·조직 overlay·표준 조건을 해결한 run별 고정 snapshot |
| Harness 개선 | 자산 피드백을 원인·범위·후보·시험·승인·릴리스·관측·복귀로 연결. 모델 가중치 재학습은 필수 범위 아님 |
| 프로젝트 배포 | 회사 기준선 선택·프로젝트 테일러링·승인 절차/TMP의 파일 또는 검증된 adapter 전달 |
| 정비 증적 / 지적 자산 | 원본·변환·보정·불확실성을 보존한 REC / 권한·범위 검토 후 재사용할 범용 사례·교훈. 서로 대체하지 않음 |
| 적용 표준 구성 | 표준 판·역할·적용 범위·사유를 묶은 StandardProfileRevision. 기준선에서 불변 참조 |
| 통합 구축 / 추가 적용 | integrate_new / augment_baseline. 전자는 복수 기준의 공동 설계, 후자는 기존 승인 기준선에 대한 증분 확장 |
| 표준 간 대응 | equivalent/overlap/contains/unique/conflict/unknown 관계. 원천 요건을 삭제하지 않는 별도 판 객체 |
| 자체 점검 | 동일 사용자가 수행/정리한 자료를 점검하는 운영상 평가 |
| GAP | 외부 표준 요건에 대한 내부 자산의 커버리지 공백 |
| NCR / 개선 항목 | 확정 부적합에 대한 기록 / 원인·조치·개정·효과 확인을 연결하는 업무 객체 |

## 3. 범위·행위자·권한

### 3.1 행위자

| 행위자 | 허용 작업 | 제한 |
|---|---|---|
| 초기 전문 운영자 | 등록·검토·편집·승인·백필·자체 점검·개정·설정 | 같은 사람이 역할을 바꿔도 독립 심사원으로 간주하지 않음 |
| 현장 작성자·제출자 | 배포 절차/TMP 사용·파일/외부 시스템 제출·사실 확인 | 초기 플랫폼 구축 계정 없음; 본인 프로젝트 범위·확인된 사실만 제공 |
| 전문팀의 논리 역할 | 표준 관리자·프로젝트 배포자·정비 검토자·지적 자산 검토 | 같은 계정의 역할 표기만으로 독립성/다중 인증을 보장하지 않음 |
| AI agent | 허용 자료 분석·추천·초안·QA·원인 가설 | 인간 승인·실제 서명·미확인 수행 사실을 만들 수 없음 |
| worker/tool | run 명세에 지정된 추출·파일 생성·허용 도구 호출 | 승인 경로 밖 쓰기·임의 명령·기본 외부 push 금지 |
| 외부 시스템 | 허용 프로젝트 배포물 수신·현장 결과 회수 | adapter capability·remote revision·receipt 검사; 코어 승인본 자동 덮어쓰기 금지 |

인증 사용자가 하나라도 actor_type과 실제 user_id를 모든 결정에 기록한다. 내부 사용자 권한은 넓게 제공하되 AI·도구 권한은 작업별로 좁힌다. 기존 6역할 RBAC는 확장 참고이며 S1에서 6개 가상 계정을 만들지 않는다.

### 3.2 릴리스 범위

S0는 엔진·저장소·배포 기술 검증, S1은 Harness 지침/템플릿/설정 개선 루프·두 핵심 구축 모드·기본 구성 변경·승인 자산, S2는 프로젝트 배포·현장 회수/정비·증적·지적 자산·백필·최소 Do·점검·개선·Harness 코드 확장, S3는 KPI·추가 포맷·Redmine·다중 제공자 확장이다. S1/S2의 Must는 해당 단계의 출시 필수다. S3를 미리 구현해야 S1이 완료되는 구조로 만들지 않는다.

### 3.3 공통 업무 규칙

| ID | 규칙 |
|---|---|
| BR-01 | 원본 자료는 불변. 재업로드·OCR·변환·수정은 새 revision 또는 파생물이다. |
| BR-02 | 공식 기준선은 사람 승인 후 발행. 생성 완료·QA Pass·고점수 추천만으로 승인하지 않는다. |
| BR-03 | 표준·원문 판·요건·자산·WI/TMP·REC를 revision 단위로 참조한다. '최신판' 링크만 저장하지 않는다. |
| BR-04 | 조직·project/org/common scope·업무 사건을 구분한다. 조직 간 자료를 AI context에 섞지 않는다. |
| BR-05 | 같은 정보의 출처가 상충하면 상태를 표시하고 사용자가 해결한다. 미확인은 null/unknown이다. |
| BR-06 | backfilled_at, 원 수행일, 추출일, 승인일을 별도 기록한다. 과거 승인자·수행 사실을 소급 생성하지 않는다. |
| BR-07 | 임의 원천 지시로 도구·키·외부 전송을 활성화하지 않는다. 자료의 보관/AI/인용/외부 제공 권한을 분리한다. |
| BR-08 | 자산 커버리지와 이행 평가를 구분한다. 백필·예시·미평가를 준수 증거로 자동 합산하지 않는다. |
| BR-09 | 자체 점검은 자체 점검으로 표기한다. 독립 심사와 다인 quorum은 S1/S2의 제공 기능이 아니다. |
| BR-10 | 동일 run 요청·승인·REC·개선 큐·발행 재시도는 멱등적이다. 취소 후 늦은 결과는 승인본을 바꾸지 않는다. |
| BR-11 | RFP/입찰 명세는 영속 기준 source intake에서 제외한다. 프로젝트 산출물은 evidence intake로 수용한다. |
| BR-12 | 기준선 교체는 기존 REC·과거 평가를 재작성하지 않는다. 새 기준 평가와 영향 참조를 별도 추가한다. |
| BR-13 | 대화의 실행·수정은 typed command와 실제 domain mutation으로 연결한다. 제안·요청·실제 완료를 구분한다. |
| BR-14 | 자연어 승인과 카드 승인은 동일 gate 정책을 적용한다. 모호한 동의·계획 승인을 최종 발행 승인으로 확대하지 않는다. |
| BR-16 | 화면 state·stream·Agent 문장은 실제 run/receipt/gate 상태와 연결한다. 연결 중단은 작업 취소가 아니며 채팅 checkpoint는 승인본 rollback이 아니다. |
| BR-17 | 도구 결과 기반 UI는 허용한 카드 schema와 renderer만 사용한다. 모델의 임의 HTML·JS·action은 실행하지 않는다. |
| BR-15 | 조직·대상 revision·결정·허용 범위·run은 구조화 상태다. 메시지 요약은 원 기록을 참조하고 권한이나 실제 상태를 바꾸지 않는다. |
| BR-18 | 통합은 활동·자산의 재사용이다. 원천 표준별 의무·판·조건·출처·충족 링크를 삭제하거나 공통 요약으로 대체하지 않는다. |
| BR-19 | 추가 적용은 base_baseline을 고정한다. 무변경 자산 판을 재사용하고 기존 의무의 회귀를 검증하며 전체 재생성은 별도 범위 결정 없이는 금지한다. |
| BR-20 | 기준 표준의 역할·유사도·최대 엄격도만으로 동등·충족·상충 해결을 자동 확정하지 않는다. 적용 의무의 미해결 누락·상충은 발행 차단이다. |
| BR-21 | 표준별 적용 normative 원 요건으로 커버리지를 독립 계산한다. N/A는 사유와 별도 집계하고 분모에서 제외하며 공통 그룹 수를 대체 분모로 쓰지 않는다. |
| BR-22 | 표준 구성·관계·추가 계획·link-only도 판과 승인 snapshot에 포함한다. 제거·교체 시 남는 표준의 공통 자산과 과거 기록을 보존한다. |
| BR-23 | 자산 편집·초안 되돌리기는 Harness 변경 동의가 아니다. 영속 개선은 사용자 의도·scope가 확인된 별도 후보로 만든다. |
| BR-24 | 후보 생성·평가 Agent는 운영 활성 지침·소스·권한·승인 정책을 직접 바꾸거나 자기 release를 승인하지 않는다. |
| BR-25 | 조직 overlay·유형/표준 조건은 보호 정책을 약화할 수 없다. 후보/suite/base/scope 변경은 기존 평가·release 승인 무효화다. |
| BR-26 | 진행 run의 effective Harness snapshot은 고정이다. 활성화·복귀는 신규 run에 적용하며 과거 자산·REC·결정을 되감지 않는다. |
| BR-27 | 기준/후보 비교는 같은 고정 suite·비교 조건·격리 환경에서 수행한다. 원 의무 손실·권한 위반·필수 회귀 실패·미완료 평가는 release 차단이다. |
| BR-28 | 개선용 참고와 평가/보류 정답을 구분한다. 평가 자료의 scope·권한을 검사하고 의미 점수·비용·한계·실패를 별도로 표시한다. |
| BR-29 | 전문가는 표준/배포/정비/Harness를 관리하고 현장은 적용 절차/TMP를 사용한다. 전 직원에게 구축 과정을 요구하지 않는다. |
| BR-30 | 프로젝트 선택·테일러링·배포 판은 회사 기준선과 구분한다. 고유 프로젝트 요구는 회사 표준으로 자동 승격하지 않는다. |
| BR-31 | 원본→정비본→필드 출처/변환/보정→배포/WI/TMP 판을 연결한다. 원본 사실과 사후 정비·확인의 시점을 구분한다. |
| BR-32 | 자료 정비·증적 패키지가 원래 준수·승인·서명·독립 심사·인증 합격을 생성하지 않는다. 미확인·상충·제외·한계를 보존한다. |
| BR-33 | 증적의 프로젝트별 공개와 범용 지적 자산 재사용은 다른 권한이다. 검토·정보 제거/범위 제한·승인 없이 사례를 공통화하지 않는다. |
| BR-34 | 생성/다운로드/전달/수신 확인을 구분한다. mock adapter는 실제 배포가 아니며 파일 전달 후의 재배포를 완전히 통제한다고 표시하지 않는다. |

## 5. 상세 기능 요구사항 (108건)

모든 기능은 조직 범위·자료 권한·입력 revision 검사 후 처리한다. S1과 S2는 Must, S3는 Should다. 이 우선순위는 출시 단계와 함께 적용한다. 아래 인수 기준은 구현 완료의 검증 조건이며 현재 통과를 의미하지 않는다.

- 인수 기준: 프로젝트 P에 회사 자산을 선택하면 무변경 자산은 원 판을 재사용하고 테일러링만 프로젝트 새 판으로 만들며 회사 원본 hash는 같다.

#### FR-STD-04 기존 기준선에 추가 표준 증분 적용

단계 **S1** · 화면 **UI-05** · 우선순위 **Must**

- 입력·선행조건: augment_baseline 프로필·base_baseline·추가 표준 판·기존 자산/링크
- 처리·업무규칙: 추가 요건을 재사용 가능/보완 필요/신규 필요/상충/판단 대기로 분류한다. 기존 충족 근거를 검증하고 link-only도 변경에 포함한다. 변경 없는 자산은 같은 doc_id/revision을 재사용하며 영향 있는 대상만 새 revision으로 만든다. 전체 재생성은 별도 범위 변경 결정 없이는 수행하지 않는다. 기존 표준 의무의 회귀 검사를 포함한다.
- 산출물: ExtensionPlanRevision·대상별 ChangeSet·기존/추가 표준 검증 결과
- 예외 처리: base 변경·근거 없는 재사용·기존 의무 훼손 시 재검토; 이미 적용된 동일 표준 판은 변경 없음 또는 명시 재평가
- 인수 기준: 기존 A 기준선에 B를 추가하면 무변경 자산의 ID·revision·hash가 동일하고 변경 대상만 새 판이며 A 요건을 잃은 초안은 발행되지 않는다. 같은 요청 재시도는 추가 기준선을 중복 발행하지 않는다.

- 기존 자산·구현 구분: 증분 설계·회귀 검사 신규; 기존 변경 묶음 재사용


#### FR-STD-05 표준별 고유·상충 조건의 명시적 처리

- 인수 기준: 상충 사례에 권한 있는 근거가 없으면 발행이 막히며 scope 분리 후 각 표준의 조건이 해당 활동·필드·자산에 연결된다.

#### FR-STD-06 표준별 독립 커버리지·공통 재사용 조회

하네스에 전달하는 과거 포맷은 어댑터가 생성한다. 예를 들어 `_state.yaml`, `mapping_draft.yaml`, `backfill_payload.yaml`, `trace.jsonl`을 엔진 호환 출력으로 만들 수 있으나 이를 DB 상태와 무제한 양방향 편집하지 않는다. `verdict_type`, `scope_type`, 기존 doc_id 등 의미 있는 키는 보존한다.

## 8. 상태 전이와 승인 정책

| 객체 | 정상 전이 | 예외·재개 |
|---|---|---|
| 원천 자료 | uploaded → validated → extracted → needs_review → confirmed | unsupported/rights_blocked/extract_failed; 수정 후 새 run |
| Harness 개선 | captured → triaged → scoped → proposed → evaluating → review_ready → released → observing → verified | rejected/deferred/needs_changes; 자산 개선과 별도 상태 |
| Harness 후보 | draft → validated → evaluation_ready → evaluated → approved → released | failed/inconclusive/stale면 평가·승인 재수행 |
| Harness 활성화 | prepared → approved → activated | 포인터/호환 충돌은 차단; 이전 release 복귀도 새 결정·activation event |
| 프로젝트 배포 | selected → tailored → reviewed → approved → packaged → delivered | 전달과 수신 확인 별도; 기준/판 변경은 새 배포 revision |
| 현장 정비 | received → extracted → bound/review_pending → normalized → clarified/reviewed → recorded | 미확인/상충 보존·원본 불변; 사후 정비와 원 수행일 구분 |
| 증적/지적 자산 | drafted → reviewed → approved → exported/published | 권한·한계·민감 정보 검토; 회사 재사용은 별도 결정 |
| 표준 적용 구성 | draft → reviewed → approved → active → superseded | 기준선 발행 시 활성화; 구성·판 변경은 새 revision |
| 표준 간 관계 | proposed → reviewed → confirmed / unknown / rejected | 원 요건·scope 변경 시 재검토; 후보를 충족 근거로 사용 금지 |
| 추가 적용 계획 | drafted → reviewed → approved → implementing → validated → published | base 변경·기존 의무 퇴행 시 재계획; 발행은 별도 gate |
| 적용요건 | draft → reviewed → approved → superseded | 보류는 needs_review; 제외는 applicability=N/A+rationale |
| 자산 revision | draft → qa_ready → review_ready → approved → active → superseded/deprecated | rejected → draft; active 직접 수정 불가 |
| Run | queued → running → waiting_review → running → completed | failed/needs_recovery/cancel_requested/cancelled; 같은 run 재개 이력 |
| Gate | open → approved/rejected/cancelled/expired | snapshot 변경은 invalidated 후 새 gate |
| Backfill batch | scanned → extracted → matched → mapping_review → field_review → approved → recorded | excluded 파일 분리; 원천/필드 변경 시 승인 재검토 |
| Finding | draft → confirmed/rejected → linked_to_improvement | 새 근거는 새 finding revision |
| Improvement | proposed → triaged → planned → approved → implementing → implemented → effect_verified → closed | defer/rejected/reopen; implemented와 closed 분리 |
| 발행 | prepared → approved → writing → committed → indexed → active | interrupted → recovery_required; commit/manifest로 재조정 |

Task는 defining → planned → executing → waiting_decision → executing → completed로 진행하며 interrupted/failed/replanned 상태를 둔다. Conversation과 Task는 Run과 별도이므로 대화 한 개에 여러 하위 run·gate가 연결되고 브라우저 재접속으로 새 run이 만들어지지 않는다.

사용자 1명이 검토와 최종 승인을 담당할 수 있지만, 승인 결정은 별도 객체로 저장한다. 승인 채널은 대화/카드/상세 패널 중 무엇이든 동일 snapshot·권한·중복 방지 규칙을 적용한다. AI 자동 retry가 approval을 만들어 내지 않는다. approval 이후 파일·필드·입력 hash가 바뀌면 새 승인을 요구한다.

### 발행 일관성 프로토콜

1. base baseline과 변경 파일 hash, 적용 표준 구성·관계·원 의무 배분·link-only 변경 hash를 고정하여 manifest를 작성한다.
2. 사용자가 해당 snapshot을 승인한다.
3. 조직 publish 잠금을 잡고 base/hash를 재검사한다.
4. 내부 private Git에 변경 묶음을 commit하고 commit/manifest를 durable하게 기록한다.
5. 동일 manifest로 DB revision/link와 색인을 갱신한다.
6. 완료 후 active_baseline을 전환한다. commit 후 DB 갱신 전 장애는 manifest로 idempotent recovery한다.

HTTP 응답 실패가 발행 실패를 뜻하지 않을 수 있으므로 client 재시도는 ChangeSet ID와 동일 idempotency key를 사용한다. 사용자에게는 복구 중/발행 완료의 실제 상태를 표시한다.

## 12. 출시 완료 기준

S0: 대화 목표→TaskPlan→typed command→실제 run→대화 승인→재개를 추가로 검증한다. 실제 엔진 start·event·gate resume·cancel·file allowlist를 허용 자료로 검증. 인터랙티브 터미널에 사람이 명령을 대신 입력하는 데모만으로 통과시키지 않는다.

S1: S1 Must 기능과 해당 NFR, AT-01~03/05~07/13~14/16~21/23~26/28~45의 해당 부분 통과. 사용자에게 원천 등록부터 승인 자산까지 실제 서버에서 인수 가능. 다중 표준 통합과 기존 기준선에 추가 표준 적용 두 모드를 모두 실제 실행·저장·발행으로 검증해야 하며 단일 표준 데모만으로 완료하지 않는다. HAR-01~09의 피드백→지침/템플릿/지원 설정 후보→격리 평가→승인→활성화→관측/복귀 루프도 실제 서버에서 인수한다. 임의 공개 배포·기본 키·샘플 비밀번호 없음.

S2: S2 Must와 AT-04/08~12/15/22/27/46~56 및 기존 회귀 통과. 최소 1건의 회사 기준선→프로젝트 절차/TMP 배포→실제 파일 작성→회수·정비→증적 패키지→검토된 지적 자산→표준/Harness 개선 연결을 완료한다. 기존 원천→자산→백필/수행→점검→개정→효과 확인도 유지한다. 단일 기능 화면만 구현한 상태를 전체 v1 완료로 간주하지 않는다.

### 15.1 기본 화면과 탐색 구조

#### 3.1 첫 화면

페이지 제목은 **어떤 프로세스 업무를 진행할까요?**다. 현재 조직, 큰 목표 입력창, 자료 첨부, 예시 시작 문장 3개, 이어할 업무를 배치한다. 첫 화면의 핵심은 자산 개수나 그래프 대시보드가 아니라 업무 시작/재개다.

예시 시작 문장: **A와 B를 통합해 공통 업무는 한 번만 수행하도록 만들어 줘 / 기존 A 기준선에 B를 추가하고 필요한 부분만 바꿔 줘 / 이 산출물을 표준 기록으로 백필해 줘**. 단일 표준 구축·개선 예시는 더 보기에서 제공한다. 예시를 누르면 입력창에 문장을 넣고 사용자가 보완·전송한다. 누르는 순간 임의 조직/표준으로 실제 작업을 시작하지 않는다.

조직이 없으면 대화에서 조직명·업무 범위를 질문한다. Agent가 프로필 후보를 요약해 사용자가 정정하면 저장한다. 조직 설정 폼 방문은 필요하지 않다. 키 설정이나 자료 이용 권한처럼 필요한 운영 조건은 그 단계에서 관련 결정/설정 패널로 연결한다.

#### 3.2 기본 탐색

왼쪽 탐색은 새 업무 / 진행 업무 / 검토 대기 / 완료 업무 / 자료·자산 찾기 / Harness 개선 / 설정이다. Harness 개선은 UI-14 업무이며 같은 대화·Canvas shell에서 진행한다. 업무 항목에는 제목·조직·실제 상태·마지막 의미 있는 변경·결정 필요 수를 표시한다. 폴더와 표준별 분류는 자료 찾기 안에서 제공한다.

업무는 사용자 목표 단위다. 대화 1개에 ingest→plan→backfill→check처럼 여러 run이 연결될 수 있다. 별도 subagent 채팅을 기본으로 만들지 않으며 메인 Agent가 사용자와 대화한다. 작업 상세를 펼치면 담당 전문 agent와 실제 수행 흔적을 볼 수 있다.

#### 3.3 Desktop 공간 제안

1440px 기준: app header 높이 56px, task sidebar 240px, 본문 좌우 padding 각 24px, 열린 Canvas와 대화 사이 gap 24px. 남는 1128px에서 대화 520px·Canvas 608px를 기본으로 한다. 좌우 폭은 조절 가능하며 최소 대화 440px·Canvas 480px를 지킨다. 이 숫자는 초안 설계 목표이며 사용성 검토 후 조정한다.

Canvas가 닫혀 있으면 대화 column 최대 800px를 중앙 정렬한다. 검토할 산출물이 생기면 카드 클릭 또는 관련 응답 완료 시 Canvas를 열되 사용자의 현재 편집·검토 대상을 강제로 바꾸지 않는다. header에는 업무명·조직·기준선·실제 상태·산출물 열기·작업 상세를 둔다.

```text
┌ 업무명 · 조직 · 기준선 · 실제 상태 ─────────────── 작업 상세 ┐
│ 업무 목록 │ 대화·계획·질문·결정 카드 │ 원문 / 자산 / 변경 Canvas │
│           │                       │ 선택 문단 → 대화로 수정   │
│           │ 완료 단계와 다음 판단  │ 근거·판·QA·변경 이력       │
│           │ 맥락 chip + 입력창     │ 검토 중 대상 유지          │
└───────────┴───────────────────────┴────────────────────────────┘
```

표는 Canvas 안에서만 필요한 범위로 사용한다. task sidebar·conversation·canvas에 같은 통계 카드를 반복 배치하지 않는다.

#### 3.4 좁은 폭과 mobile

1280px 미만은 sidebar를 64px rail/접힘 상태로 전환하고 대화/Canvas 탭을 사용한다. 768px 미만은 단일 column이며 상단 조직·업무 상태, 대화/결과 탭, 하단 composer를 제공한다. 390px에서도 맥락 chip·핵심 결정·오류·전송은 가려지지 않아야 한다.

넓은 추적성 matrix만 내부 수평 스크롤을 허용한다. 입력문·첨부·선택 범위·scroll 위치·미결정 상태는 탭/폭 전환 후 유지한다. mobile의 긴 변경 검토는 영역별로 접고, 발행 승인 전 동일 요약과 근거에 접근할 수 있어야 한다.

### 15.2 입력창과 맥락 선택

Composer는 placeholder **목표를 알려 주세요. 자료를 붙이거나 선택한 내용을 수정할 수 있습니다.**를 사용한다. 기본 높이 약 104px, 긴 입력은 200px까지 확장하고 이후 내부 스크롤한다. 파일 첨부·자료 선택·선택한 대상·전송을 제공한다. 모델 이름·temperature·token 수는 기본 화면에서 숨기고 설정/작업 상세에 둔다.

Enter=전송, Shift+Enter=줄바꿈을 지원하되 한글 IME 조합 Enter는 전송하지 않는다. 모바일은 전송 버튼을 기본으로 한다. 전송은 message 접수와 별개 단계임을 상태로 표시하고 실패 시 작성문을 보존한다. message idempotency key로 중복 클릭·재전송을 방지한다.

파일을 끌어 넣으면 제목·유형·크기·업로드/검사/이용권한 상태와 제외 버튼을 보여 준다. 여러 파일은 처음 3개와 나머지 N개로 접되 목록을 열 수 있다. 업로드 성공과 AI 처리 허용은 별도 상태다.

입력창 위 context chips: 조직명, 기준선, 구축 모드(통합/추가), 적용 표준과 판, 선택 문서와 판, 문단/페이지/셀 위치, 이번 요청에 포함한 파일. 조직·기준선은 명시 전환, 선택 자료 chip은 제거 가능하다. `@`로 자산/요건을 검색할 때 현재 조직과 허용 범위만 검색한다. chip을 제거하면 실제 context binding도 바뀐다.

Canvas에서 문단 선택→**선택한 부분을 대화로 수정**을 누르면 `WI-… v1.2 §3` chip을 붙이고 composer에 focus를 둔다. 문장을 대신 전송하지 않는다. **이 문단만 간단히 해 줘**의 범위는 선택 revision/range이며, 선택 없는 **전체를 간단히 해 줘**와 구분한다. stale 판이면 최신 초안 확인 카드를 먼저 제시한다.

### 15.4 실제 대화 흐름 A — 표준 프로세스 구축

#### A1 목표와 자료

사용자: **첨부한 가이드와 기존 매뉴얼을 참고해 우리 조직의 개발 프로세스를 정비해 줘. 작은 프로젝트에도 적용할 수 있어야 해.**

UI: 메시지 아래 첨부 카드와 조직/자료 권한 상태를 표시한다. Agent는 기존 프로필이 있으면 조회한다. 필요한 경우 **주 적용 범위는 무엇인가요?** 질문 카드에 프로젝트 / 전사 공통 / 둘 다를 제시한다. 자료 AI 권한이 미확인이면 해당 파일만 처리 대기로 둔다.

Agent 응답: **기존 매뉴얼을 기준으로 중복·누락을 검토하고, 작은 프로젝트에서 줄일 수 있는 활동과 유지해야 할 요건을 구분하겠습니다.** PlanCard에는 자료 분석 → 적용요건 검토 → 업무 흐름 → 자산 초안 → QA·변경 검토 → 기준선 발행을 표시한다. 이미 요청한 범위의 조사·초안은 시작하며 단계마다 진행 확인을 받지 않는다.

#### A2 요건·테일러링 판단

UI: **적용 판단 2건이 필요합니다** 카드로 예외만 제시한다. 원문 EvidenceCard를 열면 Canvas가 정확한 위치로 이동한다. **A는 적용하고 B는 이번 범위에서 제외하되, 이유는 운영 대상이 아니라는 점으로 남겨 줘**를 보내면 적용요건 revision과 사유를 저장하고 Receipt를 보여 준다.

Agent가 범위를 임의 확대하면 Plan revision 변경과 영향 카드로 알린다. 제외할 수 없는 의무와 모순되면 변경 이유와 출처를 설명하고 대안을 제시한다. 사용자 표현을 그대로 적는 것과 실제 적용 판단의 타당성을 구분한다.

#### A3 자산 수정

Agent: **절차 초안과 업무지침을 생성했습니다. 기존 매뉴얼과 달라진 부분 3곳을 검토해 주세요.** Artifact/Change cards를 제시한다. 사용자에게 문서 유형별 CRUD 화면 입력을 요구하지 않는다.

사용자가 WI Canvas의 검토 단계 문단을 선택하고 **이 단계는 담당자가 한 번에 처리하게 간소화해 줘**를 보낸다. Agent는 관련 요건·역할 충돌을 확인하고 해당 범위의 새 초안을 만든다. 변경 요약·diff·근거가 카드로 보인다. **다른 대안도 보여 줘**는 승인본을 바꾸지 않는 A/B 초안을 만든다.

#### A4 발행

DecisionCard 제목은 **개발 프로세스 기준선 v1.0 발행**이다. 신규 자산·개정 자산·유지 자산·해결한 요건·남은 주의 사항·활성 기준선 변화·QA 상태를 보여 준다. 버튼은 **이 변경 묶음 발행 / 수정 요청 / 나중에 검토**다. 별도 열린 gate가 있으면 어느 결정인지 분명히 표시한다.

승인 후 **발행 중**을 표시하고 실제 publish receipt 뒤 **발행 완료**로 전환한다. 오류이면 이미 commit된/아직 활성화되지 않은 상태를 보여 주고 복구한다. OutcomeCard는 승인 기준선과 후속 행동 **실제 산출물 연결 / 이행 점검 준비**를 제시한다.

### 15.5 실제 대화 흐름 B — 산출물 백필

사용자: **이 보고서와 회의록들을 표준 기록으로 정리해 줘. 같은 회의 자료는 묶어 줘.**

Agent는 유형·scope·사건·WI 후보를 분석하고 BatchSummary **검토 가능 18 / 추출 실패 2 / 묶음 후보 6 / 판단 필요 3**를 표시한다. 이 수치는 예시이며 실제 배치 결과로만 렌더링한다. 전체 20행 표를 먼저 입력하게 하지 않고 불명확한 항목 카드를 우선 보여 준다.

사용자: **앞의 세 파일은 같은 검토 회의야. 마지막 회의록은 별도야.**

Agent는 context에 포함된 파일 ID를 확인한 뒤 그룹을 실제 수정한다. 대상이 모호하면 파일명 선택을 한 번 요청한다. 변경 Receipt와 예상 REC 수를 갱신한다. **이 파일은 작업산출물 평가 WI로 연결해 줘**는 WI revision과 TMP를 확인해 수동 매핑으로 저장하며 추천 점수를 100%로 바꾸지 않는다.

FieldIssueCard: **검토일이 두 자료에서 다릅니다. 어느 값을 기록할까요?** 각 값과 원본 위치, **미확인으로 유지**를 제공한다. **승인자가 안 보이니 미확인으로 둬**는 승인자 null을 유지한다. Agent에게 사용자의 이름을 과거 승인자로 채우도록 허용하지 않는다.

DecisionCard **백필 매핑·필드 확정**에는 그룹 수·REC 예정 수·WI/TMP 판·미확인·상충 해결·제외 항목을 표시한다. 사용자 **이 매핑으로 확정해 줘**는 해당 snapshot에 연결된다. REC는 legacy_evidence로 발행하고 원본 hash·locator·원 수행일/백필일을 별도 저장한다.

Canvas의 전체 매핑 표는 **전체 비교**를 누를 때 제공한다. 카드/대화/표 편집 결과가 한 snapshot으로 통합된다. 표를 고친 뒤 오래된 대화 승인 카드를 누르면 재검토가 필요하다.

### 15.6 실제 대화 흐름 C — 점검·개정·효과 확인

사용자: **이번 GAP의 원인을 확인하고 필요한 절차를 개정해 줘.**

Agent는 finding 기준선·관련 요건·실제 증적을 조회하고 원인 **가설/확인됨/미확인**을 나눈다. ImpactCard에는 관련 WI/TMP와 열린 업무를 표시한다. 계획에서 **절차와 양식만 수정하고 실제 기록은 바꾸지 마**를 받으면 제한을 TaskMemory와 RevisionPlan에 저장한다.

사용자는 대화에서 개정 범위를 결정하고 Canvas에서 diff와 근거를 검토한다. QA Pass 이후 개정 발행 DecisionCard를 별도로 제시한다. 발행 완료 뒤 Agent는 **문서 개정은 완료했습니다. 실제 적용 효과를 확인하려면 후속 수행 자료가 필요합니다.**라고 보고한다.

**이 새 평가표로 효과를 확인해 줘**에서 증적을 연결하고 후속 자체 점검을 실행한다. 효과가 확인되지 않으면 implemented 상태와 필요한 증적을 유지한다. **종결해 줘**만으로 없는 수행/효과 사실을 생성하지 않는다. NCR/개선 종결은 효과 확인 결과와 연결한다.

### 15.8 승인·되돌리기·기억의 제어

#### 10.1 결정 종류

계획 진행은 작업 범위 허용, 표준 간 관계 확정은 원 의무 대응 판단, 통합/추가 계획은 설계 범위, 적용요건 확정은 해석·적용 판단, 백필 확정은 매핑·필드, 기준선 발행은 공식 자산 변경이다. 어떤 종류든 target snapshot과 scope가 명시되어야 한다. **좋아, 계속해**는 유일한 활성 결정에 명확히 연결될 때 해당 범위로만 적용한다. 여러 결정이나 보통 설명 뒤의 반응이면 승인으로 처리하지 않는다.

계획을 승인한 뒤 안전한 초안 작성·QA 단계에 반복 승인을 요구하지 않는다. 명시한 범위를 넘는 외부 전송·권한 변경·원본 삭제·공식 발행은 새로운 결정을 요구한다. 버튼 default focus를 발행에 두거나 Enter가 의도하지 않은 승인을 실행하지 않도록 한다.

#### 10.2 되돌리기와 대안

초안 변경 뒤 **이 수정 되돌리기**를 제공한다. command receipt의 이전 revision과 영향 범위를 사용해 새 변경을 만든다. 메시지 기록을 삭제하거나 서버 DB를 과거 시점으로 통째로 되감지 않는다. 후속 초안과 충돌하면 영향 preview를 제시한다.

**더 간단한 대안도 만들어 줘**는 draft branch A/B로 만든다. 기준·대상 요건·유지/삭제 활동을 같은 Canvas에서 비교한다. 선택은 현재 초안 후보를 정할 뿐 발행 승인까지 대신하지 않는다. 승인 기준선 복귀는 새 ChangeSet·QA·발행 gate가 필요하다.

#### 10.3 업무 기억

**업무 기억** 패널에는 목표·범위·선택 조직/판·확인한 결정·미해결·금지 외부 전송 등이 있다. 항목별 원 대화/결정 링크를 제공한다. **이 가정은 틀렸어**는 새 정정 이력을 만들고 관련 계획/초안을 재검사한다. 과거의 실제 승인·수행 이력을 지우지 않는다.

### 15.9 Agent 행동·문장·시각 원칙

Agent는 요청한 허용 범위의 자료 분석·초안을 진행하고 필요한 판단만 묻는다. 질문은 한 번에 핵심 1개, 관련된 것 최대 3개를 묶는다. 매 응답마다 확인/진행 버튼을 넣지 않는다. 제안 기본값과 추정 근거는 표시하고 사용자가 정정할 수 있게 한다.

보여 줄 것은 **어떤 자료를 사용했는지, 무엇을 실행했는지, 왜 해당 업무 판단을 제안하는지, 실제 저장/발행됐는지**다. 모델의 숨은 내부 사고 과정을 길게 표시하지 않는다. 검토 설명은 원문과 업무 규칙에 근거한 짧은 설명이다.

문장 원칙: **초안을 생성했습니다 / 변경을 저장했습니다 / 발행을 완료했습니다 / 원본에서 확인하지 못했습니다 / 이 판단이 필요합니다.** 실패하면 성공형 문장 대신 보존 결과·실패 원인·재개 가능성을 설명한다. 실제 점검 결과와 자산 커버리지, 수동 지정과 추천 점수, 초안과 승인본을 항상 구분한다.

제품 시각 제안은 차분한 문서 업무용 shell, 중립 표면, 단일 강조색, 짧은 status text, 작은 inline evidence이다. 기본 본문 15~16px, label/metadata 12~13px 수준을 제안한다. 상태는 색뿐 아니라 텍스트/아이콘으로 표시한다. source/issue 카드를 과도한 gradient나 agent avatar 군집으로 꾸미지 않는다. light/dark theme와 focus·대비를 점검한다.

### 15.10 컴포넌트·이벤트·저장 상태 계약

ComponentRegistry는 type/schema_version→검증된 renderer를 매핑한다. 최소 타입은 goal, plan, question, context, progress, evidence, artifact, change, mapping_group, field_issue, qa_issue, decision, outcome, recovery, checkpoint다. 모델 output에 HTML 문자열을 실행하거나 arbitrary action URL을 승인하지 않는다.

Message는 text/attachment/card/reference parts와 각각의 저장 상태를 갖는다. UI event는 task_id, run_id, message_id, event_id/sequence, plan_revision, object_revision, status, card_payload_ref를 갖는다. SSE 재연결은 마지막 cursor 이후 이벤트만 읽고 동일 card ID 업데이트는 upsert한다. 여러 응답/작업이 섞여도 해당 task/run generation에만 반영한다.

SelectionRef는 asset/source revision·문단 ID 또는 page/cell range·content hash다. 카드 선택과 Canvas 선택은 같은 ContextBinding으로 연결한다. 명령 실행은 server authorization과 expected revision 검사 후 Receipt를 반환한다. 실패 result는 error/retryable/보존 결과를 카드로 전달한다.

클라이언트 보존 UI state는 열린 Canvas·선택 탭·scroll·미전송 입력·context chips다. 업무 상태·승인·run·memory는 서버 DB가 기준이다. client draft cache에는 원문/키를 불필요하게 복사하지 않고 조직 전환/로그아웃 시 민감 상태를 지운다.



## 16. 다중 표준 통합·추가 적용 규범

### 16.1 핵심 대화 흐름 D — 다중 표준 통합 구축

#### D1 시작·맥락 고정

사용자: **A와 B를 통합해 우리 조직의 프로세스를 만들어 줘. 공통 업무는 한 번만 수행하게 해 줘.**

Agent: **두 표준을 함께 설계하겠습니다. 각 원 요건은 보존하고 공통 업무만 통합하겠습니다. 적용할 A·B의 판과 조직 범위를 확인해 주세요.** ContextCard는 통합 구축, A 판, B 판, 조직·scope·이용 권한을 표시한다. 역할·판이 미확정이면 짧은 질문을 제시한다. 표준 선택 폼 방문을 강제하지 않는다.

#### D2 대응·고유 의무·상충 검토

Agent는 PlanCard에 자료 확인→원 요건 추출→대응 검토→공통/고유 설계→QA→발행을 표시한다. 질문은 원문 위치를 연결한 **공통으로 처리 가능한 관계 / 추가 조건 / 별도 활동 / 상충 / 판단 대기** 카드로 제시한다. 모든 조항을 사용자가 처음부터 매핑하게 하지 않는다.

사용자: **이 둘은 검토 활동은 같지만 B의 승인자 확인은 남겨 줘.** 서버는 관계·독립 의무·설계 배분의 새 판을 저장한다. 공통 검토 WI와 TMP에 B 조건을 추가하거나 scope별 별도 단계로 제안한다. 문장이 비슷하다는 이유로 B의 추가 의무를 삭제하지 않는다.

#### D3 결과·발행

Canvas에는 공통 흐름·고유 단계, 선택 자산이 지원하는 표준별 원 의무, 전후 diff를 제공한다. 전체 대응표는 확장 보기다. OutcomeCard와 발행 DecisionCard는 **표준별 적용 요건/완전/부분/GAP/N/A/미평가, 고유 의무 반영, 미해결 상충, 실제 QA 상태**를 보여 준다. 통합 그룹 수를 표준별 원 요건 분모로 대체하지 않는다.

버튼은 **통합 기준선 발행 승인**이다. 승인 대상에는 적용 표준 구성·관계·원 의무 배분·자산·링크 판이 포함된다. 표준별 의무 누락·상충이 남으면 차단 사유를 표시한다. 실제 발행 결과 후에만 새 기준선을 완료로 표시한다.

### 16.2 핵심 대화 흐름 E — 기존 기준선에 추가 표준 적용

#### E1 기존 기준선 고정

사용자: **현재 A 기반 프로세스에 B를 추가해 줘. 기존 문서·번호는 유지하고 필요한 부분만 바꿔 줘.**

Agent는 ContextCard에 추가 적용, 불변 base 기준선, 기존 A 판, 추가 B 판, scope를 표시한다. PlanCard에서 재사용 검증→보완/신규/상충 분류→대상별 변경→A 회귀·B 반영 QA→발행을 안내한다. 기존 자산의 전체 재생성은 하지 않는다.

#### E2 변경 검토

ChangeCard는 **재사용 가능 / 보완 필요 / 신규 필요 / 상충 / 판단 대기**로 제안한다. 무변경 자산과 링크만 추가하는 항목, 실제 본문을 바꾸는 항목을 구분한다. 카드의 수치는 실제 분석 결과다. 사용자는 **이 절차는 유지하고 B의 고유 요구는 지침의 조건부 단계로 넣어 줘**처럼 수정한다. Canvas는 추가 요건→기존 근거→필요 변경→검증 결과를 연결한다.

#### E3 회귀·발행·지속 관리

QAIssueCard는 B의 미반영 의무와 A의 기존 의무 손실을 별도로 표시한다. DecisionCard의 버튼은 **추가 표준 적용 기준선 발행 승인**이며 base·새 구성·변경 대상·무변경 판·회귀 결과를 함께 제시한다. 검토 뒤 base·관계·표준 판이 바뀌면 최신 내용을 다시 검토한다.

OutcomeCard에는 재사용·본문 변경·link-only·신규 자산과 표준별 커버리지를 표시한다. 같은 요청 재전송은 중복 발행하지 않는다. 추가 판 교체·표준 제외는 새 업무·구성 판·발행 흐름으로 진행한다. 남는 표준이 사용하는 공통 자산과 과거 증적은 보존한다.

### 16.3 두 핵심 모드의 UI 계약·인수

- 기존 Context/Plan/Question/Evidence/Change/QA/Decision/Outcome 카드 타입에 `build_mode`, `standard_profile_revision`, `standard_revision_refs`, `base_baseline`, `relation_revision_refs`, `extension_plan`, `standard_coverage_snapshots`, `regression_summary`를 검증된 업무 payload로 추가한다. 임의 카드 코드 생성은 금지한다.
- 통합/추가 모드는 자연어로 인식하고 가시적 맥락으로 확인한다. 사용자가 모드를 바꾸면 현재 초안을 즉시 파괴하지 않고 새 계획·입력 snapshot으로 변경 범위를 제안한다.
- 표준 구성 변경·관계 검토 확정·설계 범위 동의·최종 발행은 대상이 다른 결정이다. 불필요한 반복 확인을 줄이되 발행 승인을 다른 결정에서 추정하지 않는다.
- UI-03에 표준 ID·판·역할, UI-04에 원 의무·관계·고유/상충, UI-05에 통합·증분 diff·재사용 판, UI-06에 표준별 독립 커버리지, UI-11에 누락/회귀 QA·발행 snapshot을 제공한다. 모두 UI-13 대화에서 열 수 있다.
- AT-29~36의 두 핵심 모드를 실제 저장·실행·승인·발행으로 인수한다. 가상 A·B 예시는 구조 검증용이며 실제 표준 조항의 해석·적합성 판정을 대신하지 않는다.


### 16.4 처리·검증의 상세 계약

통합 계획과 추가 계획은 공통 run 종류 ingest/plan과 정책을 조합한다. `build_mode`는 제품 업무 모드이며 기존 7개 run kind에 임의 셸 명령이나 실행 종류를 자동 추가하지 않는다. 분석·QA 결과의 relation/status는 서버 schema로 검증한다. FR 의존성은 구현 기능의 선행 관계이며 integrate_new 실행을 위해 augment_baseline 업무를 먼저 수행해야 한다는 의미가 아니다.

추가 적용의 S1 기본 영향은 원 요건·자산·링크·적용 구성과 무변경 판·기존 의무의 회귀 검사다. 수행 증적·열린 평가·run 전체에 대한 TRC-03 영향 분석은 S2다. S1은 이 두 모드의 발행 안전성을 S2 도입 전에도 보장한다.

가상 정답 집합에서 원 요건 50개와 통합 그룹 40개는 다른 단위다. 각 원 의무가 적용/정당한 제외/판단 대기로 식별되고, 적용 대상은 설계 요소·출처·충족 판정에 연결된다. 관계 유사도와 검토 확정은 독립이며, 하나의 공통 활동으로 여러 원 의무를 충족하는 근거가 각각 필요하다.

커버리지 분모는 표준 판·조직 scope에서 적용 대상인 normative 원 요건 수다. N/A는 별도 표기하며 사유가 없으면 확정하지 않는다. 같은 원 요건에 링크가 여러 개 있어도 분자에는 한 번만 계산한다. 분모가 0이면 산정 불가다. 정책·절차의 커버리지와 실제 이행/증적 평가는 별도 지표다.


## 17. 프로세스 자산과 Harness의 검증된 이중 개선

### 17.1 두 개선 루프와 범위

**자산 개선:** 근거·수행 증적·점검·사용자 편집 → 해당 자산의 수정 초안 → QA·승인 → 새 자산 기준선 → 실제 이행·효과 확인.

**Harness 개선:** 자산 편집·대화 피드백·실패 관측 → 원인 가설·범위 → 지침/템플릿/규칙·도구 구성 후보 → 기준/후보 비교 시험 → 검토·승인 → 새 Harness release → 이후 작업 관측·필요 시 복귀.

둘은 FeedbackCase, 생성 run과 effective Harness snapshot으로 연결한다. 자산을 수정하는 행위가 Harness 규칙 변경의 동의가 되지 않는다. 새 Harness의 활성화가 기존 승인 자산을 자동 개정하지도 않는다. 문제 버전의 영향 자산은 별도 개선 후보와 자산 발행 결정으로 처리한다. 모델 가중치 재학습은 현재 필수 범위가 아니다.

### 17.2 피드백·원인·적용 범위

피드백은 전후 자산 revision·선택 범위·원 의무·수정 사유·사용자 의도·생성 run·기존 release를 참조한다. 관측된 누락과 원인 가설을 구분한다. 문서 내용의 오류, 잘못된 표준 해석, 일회성 예외, 조직 관행, 지침·템플릿·검증·도구 문제는 각각 다른 개선 경로다. 표준 해석 정정은 적용요건 검토에도 연결하고 없는 수행 사실은 개선 규칙으로 채우지 않는다.

범위는 이번 업무, 조직 overlay, 특정 표준 구성/문서 유형, 공통 Harness로 구분한다. 공통 승격은 새 범위·영향·평가·승인을 필요로 한다. overlay는 보호된 인증·자료 권한·승인·원본 불변 정책을 약화할 수 없다. 조직 전환·context 요약·동일 사용자 재접속에서도 개선 범위를 보존한다.

### 17.3 후보 변경·평가·릴리스

후보는 불변 base HarnessRelease에서 격리해 만든다. 지침·템플릿·지원되는 규칙/도구 설정의 diff와 기대 행동을 보여 준다. 새 실행 코드가 필요한 개선은 S2 기술 변경 경로로 분리한다. 개선 Agent가 운영 소스·활성 지침·배포 설정을 즉시 수정하지 않는다.

평가 세트는 허용된 입력 판·검토된 기대/금지 행동·표준 의무·판정 rubric·버전을 고정한다. 개선용 참고 사례와 회귀/보류 사례를 구분한다. 보류 정답을 후보 생성에 제공하지 않고 판정자는 출력과 rubric을 검토한다. 의미 평가의 단일 모델 점수나 평균 개선만으로 출시하지 않는다.

기준과 후보는 같은 suite·scope·비교 가능한 provider/model 설정·예산으로 sandbox 실행한다. 후보가 보는 사례 입력과 평가 판정용 정답을 분리한다. 운영 자산·REC·승인·외부 연동에 쓰지 않는다. 결과에는 원 의무 손실·권한 위반·기존 기능 퇴행·목표 개선·비용/지연과 실패·불확실성을 개별 표시한다. 비교 조건이 다르거나 평가가 완료되지 않으면 inconclusive이며 출시를 차단한다.

릴리스 필수 조건은 해당 보호 정책 위반·원 의무 손실·필수 회귀 실패 0건, 필수 평가 완료, 검토된 목표 행동 기준 충족이다. 의미 평가 목표값·반복 횟수·예산은 EvaluationPolicyRevision으로 시험 전에 확정하고 결과를 본 뒤 통과를 위해 바꾸지 않는다. 정책 변경은 새 평가가 필요하다. 미충족은 수정·재시험·보류로 처리한다.

### 17.4 작업별 버전·활성화·복귀

HarnessRelease manifest는 지침·템플릿·규칙 설정·도구/adapter 코드 참조·hash·provider/model 설정·부모 release·suite·평가·승인·scope를 보존한다. run 시작 시 공통 release와 조직 overlay·표준 조건을 해결한 EffectiveHarnessSnapshot을 고정한다. 진행 중 작업은 이전 버전으로 재개하고 신규 작업만 새 활성 버전을 사용한다.

활성화는 기대 포인터·snapshot 검증·잠금·감사 이력을 가진 서버 동작이다. 실패·재시도에도 단일 포인터 전환과 ActivationEvent를 남긴다. 후보·base·scope·suite·rubric이 변경되면 기존 평가·승인이 새 후보를 승인하지 않는다. 원격 모델 별칭·제공자 변화와 비결정성은 재현 한계로 기록한다.

복귀는 호환 가능한 과거 Harness를 신규 작업용으로 다시 활성화하는 결정이다. 진행 작업·승인 자산·REC·감사 이력을 되감지 않는다. 코드·DB migration의 복귀 가능 여부는 별도 검증하며 불가역 migration은 포인터 전환만으로 복원했다고 표시하지 않는다. 사후 관측의 증가와 Harness 변경의 인과를 자동 확정하지 않는다.

### 17.5 산출물·인수

산출물은 FeedbackCase, HarnessImprovement, ScopePolicy, Candidate/PatchManifest, EvaluationSuite/Run/Comparison, Release/Decision/Activation, EffectiveHarnessSnapshot, Observation/RollbackPlan과 영향 자산 후보다. 내용의 근거·버전·출처·제한과 실제 실행 결과를 연결한다.

S1은 피드백→지침/템플릿/지원 설정 후보→격리 비교→승인→버전 활성화·복귀의 전체 최소 루프를 필수로 구현한다. S2는 실행 규칙·parser·tool/adapter 코드의 격리 변경·테스트·호환성·배포 경로를 확장한다. 현재 업무의 단순 수정만으로 Harness 개선 기능을 완료했다고 보지 않는다.

AT-37~45는 S1 필수, AT-46은 S2다. 최소 사례는 WI의 반복 역할 누락을 조직 scope에서 보완하는 흐름이다. 목표 개선과 기존 표준 통합·추가·백필 미확인·승인/권한 회귀를 함께 검증하고 실패 후보가 활성화되지 않는지 확인한다. 실제 웹 앱·엔진 검증은 구현 단계에서 수행한다.


### 17.6 편집·후보·평가·활성화 UI


자산 Canvas의 선택 수정은 기본적으로 이번 자산만 바꾼다. **앞으로도 적용할 규칙으로 제안**은 별도 피드백 의도를 기록하고 전후 diff·사유·생성 run/effective Harness 버전과 연결한다. 이미 대화에서 명확하게 Harness 보완을 요청했으면 이를 반복 확인하지 않고 개선 후보를 생성한다. 활성화는 나중의 명시 release 결정이다.

UI-14는 목표·원 자산·피드백 / 적용 범위 / 변경안 / 평가 / 릴리스 / 적용 후 관측·복귀를 단계로 보여 준다. header와 ContextCard에 **현재 자산을 수정 중인지, Harness 후보를 수정 중인지**를 표시하고 공통/조직/표준·유형 scope·base release·후보 판을 명시한다. 컴포넌트는 기존 Plan/Question/Evidence/Change/QA/Decision/Outcome을 재사용하며 보류 정답·키·민감 로그를 노출하지 않는다.

예시 대화:

1. 사용자: **이 WI의 역할을 보완하고, 앞으로 이 조직의 WI에서 누락되지 않게 Harness도 개선해 줘.** 자산 변경과 Harness 후보를 별도 객체로 연결한다.
2. Agent: **현재 문서 수정과 별도로 조직 A용 지침·템플릿·역할 검사 설정 변경안을 만들었습니다. 적용 범위와 diff를 확인해 주세요.** 현재 운영 버전은 유지한다.
3. 사용자: **이 규칙은 승인자가 없는 절차에는 적용하지 않도록 해 줘.** 후보의 조건을 정정하고 이전 평가·승인을 무효화한다.
4. Agent: **기존/후보를 같은 고정 사례에서 비교하겠습니다.** 시험 진행과 결과를 실제 EvaluationRun에 연결한다. 한 사례가 나빠지면 개선·퇴행·실패를 따로 표시한다.
5. 사용자: **비교 결과를 보고 새 버전을 적용할게.** 아직 활성화하지 않는다. DecisionCard에 **이 조직의 신규 작업에 Harness 버전 적용 승인**을 제공한다.
6. 사용자 승인 후 Agent: **새 버전을 활성화했습니다. 진행 중인 작업은 기존 버전을 유지합니다.** 실제 ActivationEvent와 이후 작업 버전을 표시한다.

평가 Canvas는 사례별 기준 결과/후보 결과/원 의무·금지 행동/규칙 검사/의미 판정/비용·지연/검토 사유를 나란히 제공한다. 전체 세트는 확장 비교이며 대화에는 목표 개선·필수 회귀·차단 사유를 요약한다. 실패·inconclusive면 활성화 버튼을 이유와 함께 비활성화한다.

복귀는 **이전 Harness를 신규 작업에 다시 적용**으로 표시한다. 자산 문서 되돌리기와 구분하고 호환성·진행 작업·영향 자산 후보를 보여 준다. 평가 결과·suite·후보·scope·base 변경은 stale 카드로 처리한다. AT-37~46에서 실제 자산/후보/평가/release/포인터/과거 작업 버전을 인수한다.


## 18. 전문가 관리·현장 사용·증적·회사 지적 자산

### 18.1 목적과 두 사용자 경로

Processware는 전문가/전문팀이 회사 표준을 구축·통합·편집·검증하고 프로젝트에 절차·템플릿을 배포한 뒤, 현장의 다양한 작성 결과를 회수·정비하여 감사·감리·인증·심사 제출용 증적과 회사의 재사용 가능한 지적 자산으로 연결하는 시스템이다. 조직의 모든 구성원이 표준 구축·원천 분석·Harness 개선을 알아야 하는 구조가 아니다.

**전문가 경로:** 조직 표준 기준선 → 프로젝트 선택·테일러링 → 승인 배포 → 현장 산출물 회수·정비·사실 확인 → 증적 검토·패키지 → 지적 자산·표준/Harness 개선.

**현장 경로:** 자신의 프로젝트 절차·작성 안내·빈 양식 받기 → 익숙한 파일/업무 시스템에서 작성 → 정해진 경로로 제출 → 필요한 사실 확인에 답변. 현장 사용자는 내부 표준 통합·대화·Harness UI를 반드시 사용할 필요가 없다.

초기 개인 서버는 전문 운영자 1명으로 운용하고 현장은 파일 또는 기존 외부 시스템을 이용한다. 전문팀의 작성·검토·배포 역할은 데이터에 논리적으로 구분한다. 다중 내부 관리자·현장 로그인 포털은 추가 인증/RBAC 검증 후 확장하며 현재 단계에서 모든 조직원에게 authoring 계정을 만들지 않는다.

### 18.2 프로젝트 기준선·배포·현장 계약

프로젝트마다 회사 승인 기준선·표준 구성·선택 WI/TMP 판·scope·테일러링 사유를 고정한다. 회사 표준 수정과 프로젝트 테일러링의 승인 대상은 별개다. 프로젝트 고유 요구는 project overlay이며 영속 회사 표준에 자동 편입하지 않는다. 무변경 자산은 회사 판을 참조하고 프로젝트 변경은 새 로컬 판으로 관리한다.

파일 배포는 빈 DOCX/XLSX 템플릿, 지원되는 읽기 PDF/HTML 절차, 작성·제출 안내와 manifest를 포함한다. 빈 양식·작성 예시·실제 기록을 구분하며 변환 판·project/deployment/template ID·필드 schema·hash를 기록한다. 메타 표식은 사용자 편집으로 없어질 수 있어 수집 시 확정 근거를 다시 검토한다. 파일 생성·다운로드·외부 전달·실제 수신 확인은 서로 다른 상태다.

시스템 연동은 선언된 adapter capability·필드 매핑·remote ID/revision·receipt·멱등·오류/회수 계약을 통해 제공한다. S2는 파일 배포로 운영 가능하며 공통 연동 계약을 정의한다. 특정 제품의 실제 adapter는 선택 구현·실제 대상에서 별도 검증한다. 기존 Redmine adapter의 구체 제품 연동은 INT-01 S3 범위를 유지한다. mock 실행을 전달 완료로 표시하지 않는다.

현장 공개물에는 적용 절차·템플릿·사용 안내·제출 정보만 포함한다. 원 표준의 이용 제한 내용, 구축 대화, Harness 내부 지침, 다른 프로젝트 자산·증적, 민감 평가·키는 공개 projection에서 제외한다. 파일을 전달한 뒤의 복사·재배포를 시스템이 완전히 통제한다고 표현하지 않는다.

### 18.3 비정형 산출물 정비와 사실 확인

회수 원본·해시·외부 객체 판·수집 시점·프로젝트와 제출자를 보존한다. 작성자/제출자 사실의 확인 수준을 기록하고 로그인 전문가를 원 작성자로 대체하지 않는다. 입력 문서의 레이아웃·필드명·병합 셀·별도 첨부가 달라도 원 위치와 연결해 표준 필드로 매핑한다.

정비 값은 observed, transformed, unknown, conflicting, corrected_with_reason, subsequently_confirmed 등 검증된 상태로 구분한다. 원본과 정비본·표현/단위 변환·보정 이유·추가 증빙·검토 결정을 연결한다. transform은 설명 가능한 변환이며 없는 값을 만들어 내는 행동이 아니다. 날짜·작성자·승인·서명·수행 사실은 미확인이면 그대로 둔다.

사실 확인 요청은 본문·대상·출처를 준비하고 허용된 수동/외부 경로로 수집한다. 요청 준비 자체는 외부 발송이 아니다. 원 작성자 응답·대리 입력·첨부 증빙·확인 시점·인증 수준을 구분한다. 사후 정비·확인이 원래 시점의 승인이나 당시 절차 준수의 증명이 되지 않는다. mapping/field 확정과 REC 발행은 별도 gate다.

원 배포/TMP 판이 없거나 모호하면 후보·미확인 상태로 검토한다. 과거 산출물은 작성 당시 판에 연결하며 현재 표준과의 차이는 별도 평가로 남긴다. 같은 파일명·폴더·추천 점수만으로 배포·사건을 확정하지 않는다.

### 18.4 감사·감리·인증·심사 제출용 증적

EvidencePackageRevision은 목적·프로젝트·기간·선택 기준·원 배포 판·원본·정비 REC·원 의무 대응·field provenance·보정·전문가 검토·사후 확인·미확인/제외/한계를 묶은 불변 snapshot이다. 증적 색인 XLSX, 읽기 HTML/PDF, 허용 첨부 ZIP을 내보내고 파일·링크·합계·hash를 검증한다. 초안은 초안으로 표시한다.

자료 정비·패키지 생성과 적합 판정은 구분한다. 내부 검토/자체 점검인지 외부 심사용 제출 자료인지 명시한다. 누락 사실·미해결 상충을 꾸미거나 과거 서명·승인·날짜를 생성하지 않는다. 독립 심사·인증 합격을 시스템 산출물만으로 보장하지 않는다. 한 사람이 실제 작성·점검했다면 기존 자체 점검 정책을 적용한다.

### 18.5 회사의 지적 자산화

프로젝트 증적과 회사 범용 경험을 구분한다. 전문가가 검증한 사례·교훈·작성 패턴·프로세스 개선을 CaseAsset/KnowledgeAsset 후보로 만들고, 고객·개인·계약상 정보의 재사용/제공 권한과 비식별·범위를 검토한 뒤 REF/EX 또는 별도 지적 자산 항목으로 승인한다. 원 증적·출처·변환·승인 이력은 제한된 원 영역에서 보존한다.

재사용 예시는 실제 다른 프로젝트 증적으로 제시하지 않는다. 정비본을 생성 지침에 자동 학습·전송하지 않는다. 지적 자산에서 표준 개정이나 Harness 개선으로 연결할 때 각각의 후보·시험·승인을 거친다. 프로젝트 고유 요구·개인 습관을 회사 공통 의무로 자동 승격하지 않는다.

### 18.6 핵심 산출물·단계

제품의 산출물은 회사 표준 자산, 프로젝트별 선택/테일러링 자산, 배포 절차·템플릿·manifest, 수집 원본·정비 REC·provenance, 목적별 증적 패키지, 검토된 회사 지적 자산, 표준/Harness 개선 후보·release다.

FLD-01~10·AT-47~56은 S2 필수다. S1 회사 표준·Harness 관리 위에 S2 프로젝트 배포→현장 작성→회수→정비→증적/지적 자산→개선의 최소 폐쇄 루프를 실제 파일로 인수한다. 연동 사용 시 실제 대상 receipt를 추가 검증한다. 현장 전용 포털이나 모든 직원의 플랫폼 계정은 이 파일 기반 폐쇄 루프의 선행 조건이 아니다.


### 18.7 UI·공개 projection


전문가의 UI-13은 회사 표준·프로젝트 배포·현장 정비·증적·지적 자산·Harness 개선의 관리 shell이다. 현장 구성원에게 이 구축 대화 UI를 요구하지 않는다. 현장 공개물은 적용 절차·DOCX/XLSX 빈 템플릿·작성 예시/안내·제출 위치다. 파일이나 검증된 외부 시스템에서 작성·제출하고 필요한 사실만 확인한다. 초기 전문 운영자 계정 1개와 현장의 작성자 신원은 다른 개념이다.

UI-15 프로젝트 자산·배포: 프로젝트/회사 기준선→선택/테일러링 diff→파일 또는 adapter capability→공개 대상·형식·필수 필드→배포 승인→manifest/생성·전달·수신 상태. ContextCard에 project/deployment/WI/TMP 판을 표시한다. 카드 버튼은 **이 프로젝트 배포 승인**이며 회사 기준선 발행과 구분한다.

UI-08 현장 정비: 원본·배포 후보→Agent가 구조/필드/첨부 매핑→미확인/상충·변환·보정 카드→확인 응답 출처→전문가 검토→정비 REC. 전체 표는 보조이며 임의 작성 때문에 모든 항목을 사람이 다시 입력하지 않도록 한다. 원문/정비/diff/provenance Canvas에서 같은 판을 본다.

UI-16 증적·지적 자산: 목적/프로젝트/기간/선택 기준→원본/정비/당시 배포/한계 확인→외부 제공 필터→증적 index·bundle 생성→검토된 범용 사례 후보→재사용 권한/정보 제거/scope→회사 지적 자산 승인. **증적 패키지 내보내기**와 **회사 지적 자산으로 승인**은 다른 결정이다. 결과에는 정비가 사후에 이루어졌다는 사실과 미확인/제외를 유지한다.

대화 예: **프로젝트 P에 절차와 템플릿을 배포해 줘 → 돌아온 파일에서 임의로 바꾼 항목을 정비해 줘 → 승인자는 미확인으로 두고 이 응답을 사후 확인으로 연결해 줘 → 심사 제출용 패키지로 만들어 줘 → 고객 정보는 제거하고 범용 교훈만 회사 참조 자산 후보로 만들어 줘.** 실제 객체·판·receipt·권한·전문가 결정에 연결한다. 단계별 일반 초안 작업에 불필요한 승인을 반복하지 않는다.

현장 공개 projection과 관리자 자료의 URL/API/파일 manifest를 구분한다. 작성 안내에 표준 통합·모델 설정·Harness 규칙을 요구하지 않는다. 포털이 추가되면 field 역할·프로젝트별 인증/권한·제출 신원 확인을 검증하고 초기 개인 관리자 계정을 현장과 공유하는 방식은 사용하지 않는다. FLD-01~10·AT-47~56으로 실제 배포/작성/회수 round-trip을 인수한다.
